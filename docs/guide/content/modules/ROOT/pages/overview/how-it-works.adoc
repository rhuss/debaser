`debaser build` runs its phases in a fixed order.
It fetches upstream and the patches, rebases your own branches, resets the integration branch, and merges the patches onto it.
Then it runs the recipe's steps and the acceptance checks, and only after all of them pass does it install the build output.
Most phases can stop the run, and the exit code names the kind of stop.
xref:overview/concepts.adoc[Key concepts] defines the terms this page uses.

A run that gets through every phase ends with a summary like this one:

image::visuals/build-regular.svg["Output of a successful debaser build: the installed artifact, a timeline of the fetch, rebase, merge, verify, and accept phases, one current branch, two merged patches, the report path, and the path of the installed artifact",role=expand]

The first line of the summary names what was built, the upstream commit it was built on, the number of merged patches, and how long the run took.
What was built is the installed artifact, as a path relative to the build directory, or the integration branch when nothing is installed.
Below the timeline, the summary lists the time of each phase, the branches (one current), and the patches (two merged).
The last lines give the report path and the path of the installed artifact.

== The phases

image::build-pipeline.svg["One run of debaser build from lock and preflight to report, with the Git refs and branches the phases write, the points where a coding agent steps in, and the exit code of each kind of stop",role=expand]

The diagram shows the phases in order, the Git refs and branches they write, and the stops that branch off.
The sections below follow the same order and name what can stop each phase.
In the diagram labels, harness means the configured integration that runs the coding agent.
xref:user/stops.adoc[When a build stops] explains how to read a stop and how to go on from it.

=== Lock and preflight

`build` is one of the commands that change your clone or debaser's files, so it first takes the run lock in debaser's xref:overview/concepts.adoc#data-directory[data directory].
While another live debaser process holds that lock, `build` refuses to start.
It takes over a lock left by a process that has ended.
`build` also refuses when an earlier run is stopped or still in progress, and it says where that run stopped and which commands resume or undo it.

The preflight checks the Git version, the name of the integration branch, and the remote that debaser fetches upstream from.
That remote is the one the patch list names; when the patch list names `upstream` and no such remote exists, debaser uses `origin`.
With `--push`, the preflight also requires an `origin` remote that pushes to a repository of your own, not to the upstream repository.
debaser prepares the build directory only after every preflight check passes, so a refusal leaves no directory behind.

What stops it: a refusal, with exit 1 and nothing changed.

=== Fetch

debaser fetches the upstream branch first.
Then it fetches each patch of the patch list in order.
A pull request or a branch of another repository is fetched into a private ref under `refs/debaser/`; a pull request lands in `refs/debaser/<owner>/<repo>/pull/<number>`.
debaser uses your own branches as they are, as the local branch or the copy on `origin`.
debaser reads the project's own recipe (`.debaser/recipe.toml`) from the fetched upstream, never from a patch.

The fetch also decides which patches to merge.
A pull request that upstream has already merged is skipped.
So is a patch whose commit upstream already contains.
debaser still merges a pull request that was closed without merging, and warns about it.

What stops it: a source that cannot be fetched stops the run with exit 1, before anything is reset.
A xref:overview/concepts.adoc#pin[pinned patch] (one that the patch list fixes to a commit) is the exception: when its source is gone, debaser uses the pinned commit and warns.

=== Rebase own branches

Before the reset, debaser rebases your own branches onto the fetched upstream commit and runs the recipe steps on each rebased branch.
The merge then uses their new tips.
The rebase mode decides which branches the rebase touches: `all` (the default), `conflicting` (only branches that no longer merge cleanly), or `off`.
The `--rebase` option overrides the patch list's `rebase` setting for one run.
A pinned patch is never rebased.

What stops it: nothing.
A branch whose rebase or recipe steps fail keeps its old tip.
The report gets a xref:overview/concepts.adoc#handoff[handoff] for it: a Markdown file with the problem, its cause, and a prompt to run in that branch's checkout.
The run goes on.

=== Reset

debaser points the integration branch at the fetched upstream commit with `git checkout -B` in the build directory.
If the reset fails, debaser discards the run's state before anything is merged, so no stopped run is left behind.

What stops it: a failed reset, with exit 1 and no report.

=== Merge

debaser merges the patches onto the integration branch one by one, in the order of the patch list.
Each merge is a merge commit titled `Merge <patch>: <description>`, or `Merge <patch>` when the patch has no description.
The branch history says what each patch is.
Git's rerere records how conflicts were resolved and replays those resolutions on the next run.

When a conflict has no recorded resolution, debaser hands it to the agent that the harness runs for conflicts.
If debaser accepts the agent's resolution, it goes on with the next patch.

What stops it: without a harness, the run stops with exit 2 and names the conflicting files.
When the agent cannot resolve the conflict, the run stops with exit 5.

=== Recipe steps

debaser runs the recipe's steps in order in the build directory.
The summary and the diagram call this phase verify.
A step that fails runs once more, in case it is flaky.
When it fails a second time, debaser runs it on plain upstream: the fetched upstream commit without any patches merged.
That run uses a throwaway worktree and first runs the recipe's install step and every step before the failing one.
The run on plain upstream tells a broken upstream apart from a breaking patch.

If the step fails on plain upstream too, upstream itself is broken.
If it passes there, a patch breaks it, and debaser hands the failure to the agent that the harness runs for failing steps.
An accepted fix becomes its own commit, and the steps run again from the first one, because a fix can break a step that passed before.

What stops it: a step that fails on plain upstream too stops the run with exit 4, before any agent is asked.
A step that fails only with the patches stops the run with exit 3 when no harness is set up, and with exit 5 when the agent cannot fix the step.

=== Acceptance checks

After every step has passed, debaser runs the acceptance check of each merged patch that has one.
The summary and the diagram call this phase accept.
When the recipe names a build output, the check finds it through the `DEBASER_ARTIFACT` environment variable.
A failing check runs once more, in case it is flaky.

The first acceptance check that still fails goes to the agent that the harness runs for acceptance checks, scoped to that check's patch.
An accepted fix sends the run back to the recipe steps, which run again from the first one, followed by every acceptance check.

What stops it: without a harness, a failing acceptance check stops the run with exit 6.
When the agent runs out of attempts on the check, or the run reaches its limit on agent fixes, the run stops with exit 5.

=== Install and finish

Before the install, debaser pushes your rebased branches to `origin` when you pass `--push` or confirm the prompt on a terminal.
Otherwise it prints the push commands.
Only now does the installed artifact change.
The build output replaces the installed artifact, and debaser keeps the one from the start of the run as `<target>.prev`, where `<target>` is the install path.
When the build output does not exist, debaser warns and installs nothing.
When the recipe names no install path, debaser installs nothing.
The branch `<branch>-prev` moves to where the integration branch was when the run started, so `debaser rollback` finds the previous integration branch next to the previous installed artifact.

When the recipe sets an after-build command, it runs next.
A failing after-build command is a warning; the build itself succeeded.
After that, when you pass `--push`, debaser pushes the integration branch to `origin` with `--force-with-lease`.

What stops it: nothing, not even a failed push.
A failed push only makes the run end with exit 1 instead of 0.

=== Report

A run that finishes, or stops at a merge, a recipe step, or an acceptance check, writes a report.
The report goes into its own directory under `reports` in debaser's data directory, which by default lives in the clone's shared Git directory.
The report and the `result.json` next to it carry the final exit code.
A refusal, a failed fetch, or a failed reset ends the run with exit 1 and no report.

A stop names the reason, the build directory, and the report, and it offers `debaser continue` and `debaser rollback`.
After an exit 4, it offers only `debaser rollback`, because continuing does not fix upstream.
