`debaser build` runs the same phases in the same order every time.
It fetches upstream and the patches, rebases your own branches, resets the integration branch, and merges the patches onto it.
Then it runs the recipe's steps and the acceptance checks, and only after all of them pass does it install the build output.
When a phase cannot finish, the run stops with an exit code that names the kind of stop.

A run that gets through every phase ends with a summary like this one:

The first line names the build output, the upstream commit it was built on, and the number of patches.
Below the timeline, the summary lists the time of each phase, the branches (one current), and the patches (two merged).
The last lines give the report path and the artifact path.

== The phases

image::build-pipeline.svg["One run of debaser build from fetch to report, with the points where a coding agent steps in and the exit code of each kind of stop",role=expand]

The diagram shows the phases in order, the Git refs and branches they write, and the stops that branch off.
The sections below follow the same order and name what can stop each phase.
xref:user/stops.adoc[When a build stops] explains how to read a stop and how to go on from it.

=== Lock and preflight

`build` is one of the commands that change the checkout or debaser's files, so it first takes the checkout's run lock.
While another live debaser process holds that lock, `build` refuses to start; a lock left by a process that ended is taken over.
`build` also refuses when an earlier run is stopped or still in progress, and it says where that run stopped and which commands go on from there.

The preflight checks the Git version, the name of the integration branch, and the `upstream` remote.
With `--push`, it also requires an `origin` remote of your own, apart from upstream.
debaser prepares the build directory only after every check passes, so a refusal leaves no directory behind.

What stops it: a refusal, with exit 1 and nothing changed.

=== Fetch

debaser fetches the upstream branch first and reads the recipe from the fetched upstream, never from a patch.
Then it fetches each patch of the patch list in order.
Every ref debaser writes lives under `refs/debaser/`, so a pull request lands in a private ref such as `refs/debaser/<owner>/<repo>/pull/<number>`.

The fetch also decides which patches to merge.
A pull request that upstream has already merged is skipped.
So is a patch whose commit upstream already contains.
A pull request that was closed without merging is still merged, with a warning.

What stops it: a source that cannot be fetched stops the run with exit 1, before anything is reset.
A pinned patch is the exception; when its source is gone, debaser uses the pinned commit and warns.

=== Rebase own branches

Before the reset, debaser rebases your own branches onto the new upstream and builds their new tips.
The rebase mode decides which branches it touches: `all` (the default), `conflicting` (only branches that no longer merge cleanly), or `off`.
The `--rebase` option overrides the patch list's `rebase` setting for one run.
A pinned patch is never rebased.

What stops it: nothing.
A branch that cannot be rebased keeps its old tip, gets a handoff in the report, and the run goes on.

=== Reset

debaser points the integration branch at the fetched upstream commit with `git checkout -B` in the build directory.
If the reset fails, debaser drops the run, so the checkout stays as it was.

=== Merge

debaser merges the patches onto the integration branch one by one, in the order of the patch list.
Each merge is a merge commit titled `Merge <patch>: <description>`, so the branch history says what each patch is.
Git records how conflicts were resolved and replays those resolutions on the next run.

When a conflict has no recorded resolution, debaser hands it to the coding agent configured for conflicts.
If debaser accepts the agent's resolution, it goes on with the next patch.

What stops it: without an agent, the run stops with exit 2 and names the conflicting files.
When the agent cannot resolve the conflict, the run stops with exit 5.

=== Recipe steps

debaser runs the recipe's steps in order in the build directory.
A step that fails runs once more, in case it is flaky.
When it fails a second time, debaser runs it on plain upstream in a throwaway working directory, with every earlier step first.
That rerun tells a broken upstream apart from a breaking patch.

If the step fails on plain upstream too, upstream itself is broken.
If it passes there, a patch breaks it, and debaser hands the failure to the coding agent configured for checks.
An accepted fix becomes its own commit, and the steps run again from the first one, because a fix can break a step that passed before.

What stops it: a step that fails on plain upstream too stops the run with exit 4, before any agent is asked.
A step that fails only with the patches stops it with exit 3 when no agent is configured, and with exit 5 when the agent cannot fix it.

=== Acceptance checks

After every step has passed, debaser runs the acceptance check of each merged patch that has one.
When the recipe names a build output, the check finds it through the `DEBASER_ARTIFACT` environment variable.
A failing check runs once more, in case it is flaky.

The first check that still fails goes to the coding agent configured for acceptance, scoped to that check's patch.
An accepted fix sends the run back to the recipe steps, which run again from the first one, followed by every acceptance check.

What stops it: without an agent, a failing acceptance check stops the run with exit 6.
When the agent cannot fix the check, or the agent's fixes reach their limit, the run stops with exit 5.

=== Install and finish

The installed copy changes only at this point, after every step and every acceptance check has passed.
The build output replaces the installed artifact, and the copy from the start of the run is kept as `<target>.prev`.
When the build output does not exist, debaser warns and installs nothing.
The branch `<branch>-prev` moves to where the integration branch was when the run started, so `debaser rollback` has both halves of the previous build.
When the recipe names no install path, nothing is installed, and the summary names the integration branch as the result.

When the recipe sets an after-build command, it runs next.
A failing after-build command is a warning; the build itself succeeded.
With `--push`, debaser pushes the integration branch to `origin` with `--force-with-lease`.

What stops it: nothing, because the install has already happened.
A failed push still ends the run with exit 1.

=== Report

Every run writes a report into its own directory under `reports` in debaser's data directory, which by default lives in the clone's shared Git directory.
The report and the run's result carry the final exit code.

A run that stops writes its report too.
The stop names the reason, the build directory, and the report, and it offers `debaser continue` and `debaser rollback`.
After an exit 4, it offers only `debaser rollback`, because continuing does not fix upstream.
