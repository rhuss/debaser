debaser needs a recipe to know how to check, build, and install your project.
Its generic recipes cover Bun and TypeScript projects (`bun-ts`) and Rust projects built with Cargo (`rust-cargo`).
When neither generic recipe matches your project and no other recipe is in place, a build stops with `no recipe matches this project; debaser has bun-ts, rust-cargo`.
This page writes a local `recipe.toml` for an example project, checks it with `debaser recipe`, builds with `debaser build`, and shows how to hand the recipe to the project.

You need a clone with a patch list.
Without one, debaser refuses with `+there is no patch list yet; add a patch first with `debaser add <source>`+`; xref:user/first-build.adoc[Your first build] sets one up.

== The example project

The example is `example/notes`, a fictional Python command-line tool; every detail of it on this page is made up.
notes manages its dependencies with `uv` (`pyproject.toml` and `uv.lock`).
Its tests live in the `tests` directory and run with `python -m pytest`.
Its build script `build.py` writes the tool as a single file to the path after `--output`.
notes has no `bun.lock`, `bun.lockb`, or `Cargo.toml`, so neither generic recipe detects it, and notes commits no recipe of its own.

Replace the commands below with the ones your project uses.

== Step 1: find the place for the local recipe

A local recipe is the file `recipe.toml` in the data directory, next to `patches.json`.
debaser reads a local recipe as it is.
A recipe the project commits needs your approval first; Step 6 shows how to trust one.
By default the data directory is `debaser` inside your clone's shared Git directory (`.git/debaser` in a plain clone); `--dir` or `DEBASER_DIR` moves it.

. In your clone, show where the data directory is.
+
Check: the `data` line names the data directory, and the `config` line ends with `(local recipe: none)`.
+
[source,bash]
----
debaser list
----
// expect: contains "local recipe: none"
+
When the `config` line names a path instead of `none`, a local recipe exists already.
Edit that file instead, and skip the `cat` command in Step 2, which would overwrite it.

== Step 2: write the recipe

The recipe for notes defines three steps: `install`, `test`, and `build`.
It also marks `install` as the install step, sets the build output and the installed artifact, and lists one glob for temporary files.

. Write the recipe to `recipe.toml` in the data directory.
With a data directory other than the default (Step 1), adjust the path.
+
[source,bash]
----
cat > "$(git rev-parse --git-common-dir)/debaser/recipe.toml" <<'EOF'
project_name = "notes CLI"
leftovers = ["**/__pycache__/**"]

[install]
step = "install"
triggers = ["uv.lock", "pyproject.toml"]
marker = ".venv"

[artifact]
output = "dist/notes.pyz"
install = "dist/notes-custom.pyz"

[[steps]]
name = "install"
run = ["uv", "sync"]

[[steps]]
name = "test"
run = ["uv", "run", "python", "-m", "pytest", "{tests}"]
tests = ["tests"]
timeout = 600

[[steps]]
name = "build"
run = ["uv", "run", "python", "build.py", "--output", "{output}"]
EOF
----

What each part does:

* `project_name` is the name debaser puts into the prompts for a coding agent.
* `leftovers` lists globs of temporary files that debaser never commits with a fix.
* `[install]` names the step that installs the dependencies.
debaser runs it when `.venv` is missing from the build directory.
debaser also runs the install step when `uv.lock` or `pyproject.toml` differs between the merged result and the commit the build directory started the run on.
Otherwise it skips the install step.
* `[artifact]` sets two different paths.
`output` is where the build step writes, and steps get it as `+{output}+`.
`install` is where debaser copies that file once every step has passed, and every acceptance check too (Step 5 adds one).
Both paths are relative to the build directory, and debaser installs only when both keys are set.
* Each `+[[steps]]+` table is a step, and debaser runs them in this order.
`run` is the command with one argument per array element.
* On a full run, `+{tests}+` becomes the step's `tests` list, here `tests`.
* None of the steps sets `parser`, so debaser reads their logs with the generic scan, which picks out path-like words from the log.
* When a step fails, debaser runs it once more in case the failure is flaky.
Only the `bun-test` parser narrows that rerun to the failing files, so here a failing `test` step reruns the whole command.
* `timeout = 600` kills the `test` step after 600 seconds.

xref:recipe-author/steps.adoc[Steps, install, and artifact] explains every one of these keys.

== Step 3: check the recipe

`debaser recipe` reads every recipe layer, checks it, and prints the effective recipe with the layer each value comes from.
It rejects an unknown key or a value of the wrong type, and the error names the file and the key.

. Show the effective recipe.
+
Check: the first line reads `debaser recipe · local` followed by the path of your file, and the steps table lists `install`, `test`, and `build`, each with the layer `local`.
+
[source,bash]
----
debaser recipe
----
// expect: exit 0 and contains "recipe · local" and contains "pytest"
+
The first line names no generic layer, because detection found none for notes.
The `test` row shows `+({tests} = tests) (timeout 600s)+` after the command, and the `PARSER` column shows `-` for all three steps.
The second table lists `project_name`, the three `install` keys, both `artifact` keys, and `leftovers`.

xref:recipe-author/recipes.adoc#see-the-effective-recipe[See the effective recipe] explains the output.

== Step 4: build with the recipe

. Build.
+
Check: the end of the output names the installed artifact.
In plain output, the summary starts with `debaser: built dist/notes-custom.pyz`, the installed artifact relative to the build directory.
On a color terminal, the last lines contain `build done · artifact` followed by the absolute path, ending in `dist/notes-custom.pyz`.
Skip this check when the build stops; xref:user/stops.adoc[When a build stops] explains each stop.
+
[source,bash]
----
debaser build
----
// expect: exit 0 and contains "dist/notes-custom.pyz"

When `dist/notes.pyz` does not exist after the build, debaser installs nothing, warns `warning: the build output dist/notes.pyz does not exist; nothing was installed`, and the summary names the integration branch instead.

== Step 5 (optional): add an acceptance check

The recipe's steps show that the combined build works.
An acceptance check shows that one patch still does what it is for.
It is a command in that patch's entry in `patches.json`, and debaser runs it after every step has passed.

Say one of your patches adds a `stats` command to notes that prints a line such as `notes: 12`.
The `acceptance` object for that patch looks like this:

[source,json]
----
"acceptance": {
  "run": ["uv", "run", "python", "{output}", "stats"],
  "match": "^notes: [0-9]+$"
}
----

`+{output}+` is the build output, `dist/notes.pyz` in the build directory.
The acceptance check passes when the command exits with 0 and `match` is found in its output.

. Open the patch list and add the object as a key of your patch's entry, next to `source`, `description`, and `added`, with a comma after the key before it.
Save the file.
As in Step 2, the path assumes the default data directory.
+
[source,bash]
----
"${EDITOR:-vi}" "$(git rev-parse --git-common-dir)/debaser/patches.json"
----

. List the patches.
+
Check: the description of your patch ends with `(with check)`.
+
[source,bash]
----
debaser list
----
// expect: exit 0 and contains "(with check)"

xref:recipe-author/acceptance-checks.adoc[Acceptance checks] covers the other keys and what happens when a check fails.

== Step 6 (optional): share the recipe with the project

A project can commit a recipe as `.debaser/recipe.toml`.
debaser reads that file with Git from the fetched upstream commit, never from a patch.
The project's recipe therefore takes effect only once it is on the upstream branch your patch list follows.
Unlike your local recipe, debaser uses it only after you trust it.

In the commands below:

* `<branch>` is a new branch name of your choice.
* `<upstream-branch>` is the upstream branch your patch list follows.
* `<upstream-remote>` is the remote debaser fetches it from.

That remote is `upstream` by default, or `origin` when the clone has no `upstream` remote.

. Put the recipe on a new branch based on upstream and commit it.
+
[source,bash]
----
git switch -c <branch> <upstream-remote>/<upstream-branch>
mkdir -p .debaser
cp "$(git rev-parse --git-common-dir)/debaser/recipe.toml" .debaser/recipe.toml
git add .debaser/recipe.toml
git commit -m "Add a debaser recipe"
----

. Propose the branch to the upstream project, and wait until it is merged.

. On a terminal, review and trust the project's recipe.
`debaser trust` fetches the upstream branch, shows what the recipe runs, and asks `Trust it? [y/N]`.
Answer `y` after you have read the commands.
+
Check: debaser reports the recipe as trusted or already trusted.
+
[source,bash]
----
debaser trust
----
// expect: exit 0 and matches /debaser: trusted|already trusted/
+
Without a terminal, skip this step: `debaser trust` needs one for its question.
The next `debaser build` then asks the same question when it runs on a terminal.
Without a terminal, that build stops with exit 1 unless you pass `--trust-recipe`.

. Optional: remove your local recipe.
Your local recipe stays the top layer: its steps and keys replace those of the project's recipe, and its `leftovers` add to them.
Remove it when you want the project's recipe to apply as committed.
+
[source,bash]
----
rm "$(git rev-parse --git-common-dir)/debaser/recipe.toml"
----

. Show the effective recipe.
+
Check: the first line names `repo .debaser/recipe.toml at upstream` and a commit.
When you removed your local recipe, the line names no `local` layer; with your local recipe in place, it ends with `< local <path>`.
+
[source,bash]
----
debaser recipe
----
// expect: exit 0 and contains "repo .debaser/recipe.toml at upstream"
