The steps of a recipe are the commands that test and build the project, which debaser runs on the merged result.
This page covers the keys of a step and where a new step goes among the inherited ones.
It explains the placeholders and environment a step gets, and how failure parsers shape the rerun of a failing step.
It also covers the other keys of a recipe, except the prompts and the keys that choose layers.
These are the install step, the build output and the installed artifact, the after-build command, `leftovers`, and `project_name`.
It ends with a local recipe for a small project, written from start to finish.

xref:recipe-author/recipes.adoc[Recipes and their layers] explains the layers a recipe comes from and how they merge.

== Write a step

Each step is a `[[steps]]` table in the recipe file.
debaser runs the steps in the order the effective recipe lists them.

[cols="1,1,3",options="header"]
|===
|Key |Type |What it does

|`name`
|string, required
|Names the step.
Layers merge steps by this name, and a name may appear only once per file (`step <name> appears twice`).

|`run`
|array of strings, required
|The command and its arguments, one array element each.
The array must not be empty.

|`parser`
|string
|The failure parser that reads the step's log when it fails: `bun-test`, `tsc`, `cargo-test`, or `generic`.
Without it, debaser uses `generic`.

|`timeout`
|positive number
|Seconds before debaser kills the step.
Without it, the step has no timeout.

|`tests`
|array of strings
|What `+{tests}+` stands for when the step runs in full.
The array must not be empty.

|`before`, `after`
|string
|The name of the step a new step goes before or after.
|===

debaser rejects a misspelt parser when it loads the recipe, with `steps[<index>].parser names no failure parser (known: bun-test, tsc, cargo-test, generic)`.
A `timeout` of zero, a negative number, or a string stops the load with `steps[<index>].timeout must be a positive number of seconds`.

A step that runs past its timeout is killed together with its process group and counts as failing.
Its log ends with `(killed after <seconds>s: the step timed out)`.
debaser writes each step's output to `steps/<step>.log` in the run's report directory.

== Place a step among the inherited ones

A step in your layer either replaces a step from a lower layer or adds a new one:

* A step with the name of a lower layer's step replaces that step at its place.
It replaces the whole step, so repeat every key you want to keep, such as `parser` or `tests`.
* A step with a new name goes before the step that `before` names, after the step that `after` names, or at the end when it sets neither.
* `steps_replace = true` at the top level of your layer drops the steps of all lower layers before your steps are added.

The step that `before` or `after` names must already be in the recipe: a step of a lower layer, or a step earlier in the same file.
Otherwise debaser stops with `step <name> is placed before <other>, which no lower layer has` (or `after`).

With `steps_replace = true`, check the `[install]` table of the lower layers.
When it names a step your layer no longer has, debaser stops with `the install step <name> is not one of the recipe's steps`.
Define a step with that name, or set `install.step` to one of yours.

This layer drops the steps of the generic recipe `bun-ts` and defines its own, keeping the name `install` that `bun-ts` names as its install step:

[source,toml]
----
steps_replace = true

[[steps]]
name = "install"
run = ["bun", "install"]

[[steps]]
name = "test"
run = ["bun", "test", "{tests}"]
parser = "bun-test"
----

`debaser recipe` shows the effective steps with the layer each one comes from.

== Placeholders in commands

debaser fills three placeholders in the arguments of `run` before it starts the command.

[cols="1,3",options="header"]
|===
|Placeholder |Becomes

|`+{output}+`
|The build output path, `artifact.output`, resolved against the tree the step runs in.
Without `artifact.output`, it is `debaser-output` in that tree.

|`+{root}+`
|The tree the step runs in.

|`+{tests}+`
|On a full run, the step's `tests` list, or nothing when the step has none, so the test runner runs all tests.
On the rerun of a failing step, the failing test files, when debaser narrows the rerun to them (see <<failure-parsers-and-the-flaky-rerun>>).
|===

The tree a step runs in is usually the build directory.
When debaser reruns a step on plain upstream, the fetched upstream commit without any patches merged, it runs the step in a throwaway worktree, and when it checks one of your own branches after a rebase, in that branch's worktree.
`+{root}+` and `+{output}+` follow the tree.

`+{tests}+` as an argument of its own becomes one argument per entry, and no argument at all when the list is empty.
Inside a longer argument, such as `+--filter={tests}+`, it becomes the files as words separated by spaces, with quotes around any file name that needs them.

== Failure parsers and the flaky rerun

A failure parser reads the log of a failing step.
It gives debaser the failing files and tests, and a one-line summary for the stop and the report.
It also names the paths the failure points at, and debaser looks for the merged patches that touch them.

[cols="1,3",options="header"]
|===
|Parser |Reads

|`bun-test`
|`bun test` output: the failing tests and the files they are in.

|`tsc`
|TypeScript compiler errors (`path(line,col): error TS<number>`) and the files that have them.

|`cargo-test`
|`cargo test` output: failing tests from their `---- <name> stdout ----` blocks, files from panics and compiler locations.

|`generic`
|Any log: path-like words the failure names.
It gives no summary and no failing tests.
|===

A step that fails runs once more, in case the failure is flaky.
The rerun is narrowed to the failing test files when both of these hold:

* The parser names those files.
Only `bun-test` does, and only when every failure names its file and bun reports no error outside the failing tests.
`cargo-test` never narrows, because cargo selects tests by name, not by file.
* `run` has `+{tests}+` as an argument of its own.

Otherwise the rerun runs the whole command again.

When the rerun passes, the step counts as passed.
In plain output, the build summary adds `warning: <step> failed once and passed when run again; it may be flaky (<log>)`.
On a color terminal, the live view, the progress card that debaser redraws in place, shows `↻ retried <step> failed once, passed on retry: may be flaky` instead.
The log of the first failure stays in the report directory as `steps/<step>-flaky-<n>.log`.
When the rerun fails too, debaser tries the step on plain upstream to find out whether a patch broke it.
xref:overview/how-it-works.adoc[How a build works] follows that path to exit 3, 4, or 5.

== The install step

The install step installs the project's dependencies, for example `bun install --frozen-lockfile` in the generic recipe `bun-ts`.
debaser skips it when the dependencies are unchanged.
The `[install]` table names it and says when it runs:

`install.step`::
The name of the step.
It must be one of the recipe's steps.

`install.triggers`::
Files whose change makes the step run again.

`install.marker`::
A path in the build directory, such as `node_modules`, whose absence makes the step run.

For the step that `install.step` names, debaser decides at each build:

. With a marker that is missing from the build directory, the step runs.
. Without triggers, the step runs on every build when there is no marker, and is skipped when the marker exists.
. With triggers and no marker, the step runs when it never passed in this build directory.
debaser records a passed install step in the build directory's own Git directory, as the file `debaser-installed`, so a new or recreated build directory runs it once.
. Otherwise, the step runs when one of the trigger files changed between the commit the build directory had at the start of the run and the merged result.

A recipe without an `[install]` table runs every step on every build.

debaser skips the install step only in the build directory.
When debaser runs the steps on your own branches after a rebase, it runs every step, the install step included.
When debaser reruns a step on plain upstream, it runs the install step first in the throwaway worktree, even when the recipe lists it later.
`debaser rollback` runs the install step again after it moves the build directory back, and stops with `dependency restore failed after rollback; see <log>` when the step fails.

== Build output and installed artifact

Two keys under `[artifact]` say what the build produces and where debaser installs it:

`artifact.output`::
The path the build step writes, which steps get as `+{output}+`.

`artifact.install`::
The path where debaser puts a copy of the build output once the build has passed.

Both paths are relative to the build directory; an absolute path stays as it is.
They are different files: the build steps write the build output, and debaser replaces the installed artifact only at the end of a successful run.

debaser installs only when the recipe sets both keys.
After every step and every acceptance check has passed, it copies the build output to the install path.
The installed artifact from the start of the run becomes `<install path>.prev`.
When there was no installed artifact at the start, debaser removes an old `.prev` file.
When the build output does not exist, debaser installs nothing and warns `warning: the build output <path> does not exist; nothing was installed`.

In plain output, the build summary starts with `debaser: built <install path>`, the installed artifact relative to the build directory, or with the integration branch when nothing was installed.
On a color terminal, the live view ends with `build done · artifact <path>`, with the installed artifact's absolute path, and has no such line when nothing was installed.
Acceptance checks find the build output through `DEBASER_ARTIFACT`; xref:recipe-author/acceptance-checks.adoc[Acceptance checks] covers them.

== The after-build command

`after_build` is a command that runs once the build has fully succeeded, for example `./dist/corgi-custom reload` in the built-in recipe for `tals/corgi`.
Like `run`, it is a non-empty array with the command and its arguments.

debaser runs it after the install and before `--push` pushes the integration branch.
It runs in the build directory, with debaser's own environment but without the `DEBASER_` variables that steps get.
debaser fills no placeholders in it and sets no timeout.
Its output goes to `steps/after-build.log` in the report directory.

A failing after-build command does not fail the build.
The summary says `warning: the after-build command failed; the build itself succeeded`, and the exit code stays as it was.

== Leftovers

Build tools can leave temporary files in the build directory while they run.
`leftovers` lists globs for such files, matched against paths relative to the build directory.
debaser never commits a matching file with a fix, neither the agent's fix nor the changes `debaser continue` commits as yours.
It also treats the `.<hash>.bun-build` files of an interrupted `bun build` this way, without a glob.

[source,toml]
----
leftovers = ["**/*.tmp"]
----

The `leftovers` of all layers combine.

== Project name

`project_name` is the name debaser fills into the prompts for the coding agent, for example `Fix a failing step in a patched <name> build`.
Without it, debaser uses the repository part of the patch list's `upstream.repo`, and `debaser recipe` shows `default` as its layer.

== Environment variables for steps

Steps run with debaser's own environment plus four variables that describe the build, so the project can stamp its build with them:

[cols="1,3",options="header"]
|===
|Variable |Value

|`DEBASER_PATCHES`
|A JSON array of the merged patches, each with `source`, `display`, `commit`, and `pin` when the patch is pinned.

|`DEBASER_FORK_URL`
|The push URL of the remote `origin`, or empty when the clone has no `origin`.
From a URL with a scheme, such as `https://`, debaser removes the user name and password; an scp-style `user@host:path` stays as it is.

|`DEBASER_COMMIT`
|The commit of the tree the step runs in: the merged result in the build directory, the tree's own commit on plain upstream and on your own branches after a rebase.

|`DEBASER_MANIFEST`
|The path of `manifest.json` in the xref:overview/concepts.adoc[data directory].
debaser writes it when the steps start in the build directory, with `version`, `upstream` (`repo`, `branch`, `tip`), `commit`, `fork`, and `patches`.
On plain upstream, its `commit` is still the build directory's commit.
The steps on your own branches run before debaser writes the file in that run, so they see the previous build's file or none.
|===

Steps get these variables in the build directory, on plain upstream, and on your own branches after a rebase.
The after-build command and the install step that `debaser rollback` runs do not get them.

== Write a local recipe

A local recipe changes how debaser builds your clone without touching the project.
It lives as `recipe.toml` in the data directory, next to `patches.json`.
By default the data directory is `debaser` inside your clone's shared Git directory (`.git/debaser` in a plain clone); `--dir` or `DEBASER_DIR` moves it.

The example uses the fictional project `example/gadget`, a Bun and TypeScript command-line tool with a `bun.lock`.
debaser detects it as `bun-ts`, which brings the steps `install`, `typecheck`, and `test`, and the install step `install` with its triggers and marker.
gadget commits no recipe of its own.
Its build script `build.ts` writes the binary to the path after `--outfile`.

The local recipe keeps what `bun-ts` provides and adds what gadget needs.

. In your clone, show where the data directory is.
+
Check: the first lines name the data directory and say that there is no local recipe yet.
+
[source,bash]
----
debaser list
----
// expect: contains "local recipe: none"
+
When the line names a path instead of `none`, a local recipe exists already; edit that file instead.

. Write the recipe to `recipe.toml` in the data directory.
The command assumes the default data directory; with `--dir` or `DEBASER_DIR`, write to `<data directory>/recipe.toml` instead.
+
[source,bash]
----
cat > "$(git rev-parse --git-common-dir)/debaser/recipe.toml" <<'EOF'
project_name = "gadget CLI"
after_build = ["./dist/gadget-custom", "--version"]
leftovers = ["**/*.tmp"]

[artifact]
output = "dist/gadget"
install = "dist/gadget-custom"

[[steps]]
name = "lint"
run = ["bun", "run", "lint"]
after = "typecheck"

[[steps]]
name = "test"
run = ["bun", "test", "{tests}"]
parser = "bun-test"
timeout = 600
tests = ["src"]

[[steps]]
name = "build"
run = ["bun", "build.ts", "--outfile", "{output}"]
timeout = 300
EOF
----
+
--
What each part does:

* `lint` is a new step, placed after the inherited `typecheck`.
* `test` replaces the step of `bun-ts`.
It repeats `run` and `parser`, because a replacement does not inherit them, and adds a timeout of 600 seconds.
With `tests = ["src"]`, a full run tests only `src`; the narrowed rerun still runs only the failing files.
* `build` is a new step at the end.
It writes the binary to `+{output}+`, which is `dist/gadget` in the build directory.
* `[artifact]` makes debaser copy `dist/gadget` to `dist/gadget-custom` after a successful build, keeping the previous installed artifact as `dist/gadget-custom.prev`.
* `after_build` runs the installed binary with `--version` once the build has succeeded.
* The install step comes from `bun-ts` unchanged, so the recipe does not mention it.

The effective steps are `install`, `typecheck`, `lint`, `test`, and `build`.
--

. Show the effective recipe.
debaser reads and checks the new layer, and rejects an unknown key or a wrong type with the file and the key.
+
Check: the layers line ends with `local` and the path of your file, and the steps table lists `lint` from the layer `local`.
+
[source,bash]
----
debaser recipe
----
// expect: exit 0 and contains "local" and contains "lint"
+
xref:recipe-author/recipes.adoc[Recipes and their layers] explains the output.

. Build.
+
Check: the end of the output names the installed artifact.
In plain output, the summary starts with `debaser: built dist/gadget-custom`; on a color terminal, the last line contains `build done · artifact` followed by the absolute path, ending in `dist/gadget-custom`.
Skip this check when the build stops; xref:user/stops.adoc[When a build stops] explains each stop.
+
[source,bash]
----

----
// expect: exit 0 and contains "dist/gadget-custom"
