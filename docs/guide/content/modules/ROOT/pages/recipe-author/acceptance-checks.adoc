The recipe steps tell you that the combined build works.
An acceptance check tells you that one patch still does what it is for.
You attach it to a single patch in the patch list, and debaser runs it against the finished build.

A patch can merge cleanly and pass every recipe step while the build no longer does what the patch is for.
An acceptance check catches that case, and when it fails, debaser blames only the patch the check belongs to.

This page describes the keys of an acceptance check, shows how to add one, explains when debaser runs it and with which environment, and what happens when it fails.
It ends with the places where debaser shows the checks and their results.

== The keys of a check

An acceptance check is the `acceptance` object of a patch entry in `patches.json`.

[cols="1,1,3",options="header"]
|===
|Key |Type |What it does

|`run`
|array of strings, required
|The command and its arguments, one array element each.
The array must not be empty.
debaser runs the command without a shell.

|`exit`
|integer
|The exit code the command must end with.
Without it, debaser expects `0`.

|`match`
|string
|A regular expression in JavaScript syntax that must match the check's output.
debaser searches the standard output and the standard error of the command together.

|`timeout`
|positive number
|Seconds before debaser kills the check.
Without it, the timeout is 300 seconds.
|===

debaser validates these keys whenever it reads `patches.json`.
An invalid `acceptance` object stops the command with exit 1 and a message such as `<file>: patches[<index>] (<patch>): acceptance.timeout must be a positive number`.
A `match` that is not a valid regular expression fails with `acceptance.match is not a valid regular expression: <reason>`.

== Add a check to a patch

No debaser command adds or changes an acceptance check.
You write it into the patch's entry in `patches.json` by hand.
`acceptance` is a key debaser knows, so it stays in place when `debaser add`, `debaser remove`, or a build writes the file again.
xref:user/patch-list.adoc#edit-by-hand[Edit `patches.json` by hand] describes the file and which commands rewrite it.

The example uses the fictional project `example/widget`.
Its patch from pull request 12 adds a `--quiet` option, and its recipe sets `artifact.output` to the binary the build writes.
The acceptance check runs the binary's `status` command with the new option and expects a line that reads `ok`:

[source,json]
----
{
  "source": { "kind": "pr", "repo": "example/widget", "number": 12 },
  "description": "Add a --quiet option",
  "added": "2026-11-23",
  "acceptance": {
    "run": ["{output}", "status", "--quiet"],
    "exit": 0,
    "match": "^ok$",
    "timeout": 60
  }
}
----

`+{output}+` stands for the build output, as in a recipe step.
`"exit": 0` repeats the default and could be left out.
`"match": "^ok$"` passes when any line of the output is exactly `ok`.
`"timeout": 60` gives the acceptance check one minute instead of the default five.

. Open the patch list in a text editor.
The command assumes the default xref:overview/concepts.adoc#data-directory[data directory]; with `--dir` or `DEBASER_DIR`, open `<data directory>/patches.json` instead.
+
[source,bash]
----
"${EDITOR:-vi}" "$(git rev-parse --git-common-dir)/debaser/patches.json"
----

. In the `patches` array, find the entry of your patch and add an `acceptance` object with at least `run`.
Replace the command of the example with one that exercises your patch.

. Save the file and list the patches.
debaser reads and validates the file before it prints anything.
+
Check: the description of your patch ends with `(with check)`.
+
[source,bash]
----
debaser list
----
// expect: exit 0 and contains "(with check)"

. Build.
+
[source,bash]
----
debaser build
----

. Read the `Acceptance checks` section of the newest report.
The command assumes the default data directory; `<patch>` is your patch as `debaser list` shows it.
+
Check: the line of your patch ends with `pass`, `flaky`, or `fixed` (see <<when-fails>>).
Skip this step when the build stopped before debaser ran the acceptance checks; xref:user/stops.adoc[When a build stops] explains each stop.
+
[source,bash]
----
sed -n '/^## Acceptance checks$/,/^## /p' "$(git rev-parse --git-common-dir)/debaser/reports/latest/report.md" | grep -F -- '- <patch>:'
----
// expect: matches /: (pass|flaky|fixed)$/

== When and how a check runs

debaser runs the acceptance checks after every recipe step has passed, and installs nothing until every acceptance check has passed.
When the acceptance checks run, the build output is the file the recipe steps wrote, and the installed artifact (`artifact.install`) is still the old one.
debaser runs them in patch list order, one per merged patch that has a check.
When the build skips a patch, because upstream merged it or already contains its changes, debaser does not run its acceptance check.

Each acceptance check runs in the build directory.
debaser fills the placeholders `+{output}+` and `+{root}+` in the arguments of `run`, as it does for steps.
`+{output}+` becomes the build output resolved against the build directory, and `+{root}+` the build directory itself.
The check gets no standard input.

The acceptance check's environment is debaser's own environment plus these variables:

* `DEBASER_PATCHES`, `DEBASER_FORK_URL`, `DEBASER_COMMIT`, and `DEBASER_MANIFEST`, the same variables the steps get.
xref:recipe-author/steps.adoc#environment-variables-for-steps[Environment variables for steps] describes their values.
* `DEBASER_ARTIFACT`, the absolute path of the build output, `artifact.output` resolved against the build directory.

When the recipe has no `artifact.output`, debaser removes `DEBASER_ARTIFACT` from the environment, even when your shell sets it.
`+{output}+` still has a value then: `debaser-output` in the build directory.

An acceptance check passes when all of these hold:

* The command ends before its `timeout`.
* The command ends with the exit code from `exit`.
* With `match`, the pattern is found in the combined output.
debaser compiles the pattern with the `m` flag, so `^` and `$` match at the start and end of each line, not only of the whole output.

An acceptance check that runs past its timeout is killed together with its process group.
A command that cannot start, for example because its program does not exist, fails too, and its log holds the error.

debaser writes each acceptance check's output to `acceptance/<patch>.log` in the run's report directory, named after the patch.
The log starts with `$ <command>` and ends with a line such as `(exit 0, expected 0; pattern found: ^ok$)`, or `(killed after <seconds>s: the check timed out)`.

[#when-fails]
== When a check fails

A failing acceptance check first runs once more, in case it is flaky.
debaser keeps the log of the first run as `acceptance/<patch>-flaky.log`.
When the rerun passes, the check counts as passed with the result `flaky`.

When the rerun fails too, the acceptance check counts as failing.
debaser still runs the checks of the remaining patches before it acts, so the stop can name every failing check.
Then it takes the first failing check, in patch list order, and blames only that check's patch.
What happens next depends on the harness.

=== With a harness

With a harness configured, debaser hands the first failing acceptance check to the coding agent.
It uses the command from the harness's `tasks.acceptance` entry, or the top-level harness command when there is none (see xref:recipe-author/harness.adoc#per-task[A different agent per task]).
debaser gives the agent a prompt about that patch only, which names the patch with its description and pull request, the check's command and expected result, the build output, and the number of the attempt.
The prompt also carries the last 200 lines of the check's log.

When debaser accepts the agent's change, it commits it as `debaser: fix acceptance <patch> (agent)` with the trailer `Fixed-By: harness`.
The run then goes back to the recipe steps.
Every step runs again from the first one, followed by every acceptance check.
An acceptance check that passes after an agent fix for its patch earlier in the run has the result `fixed`.

The agent's fix also leaves a xref:recipe-author/harness-verification.adoc#handoffs[handoff] for that patch, so the fix can go back to the patch's own branch.
A handoff is a Markdown file for one patch in the report's `handoffs` directory, with the problem, its cause, and a prompt for the patch's branch.
This one shows the agent's fix commit under `Fix applied in the patched build`, next to the task of making the check pass on the patch's own branch.

Two limits apply:

* A failing acceptance check gets up to the harness's `attempts` (3 by default).
The count for an acceptance check carries over when the run goes back to the recipe steps, and resets only when the check passes.
* The agent's fixes for the whole run are capped at `attempts` multiplied by the sum of the recipe steps and the acceptance checks of patches the build does not skip.
For example, 3 attempts, 4 recipe steps, and 2 such acceptance checks allow 18 fixes.
Step fixes and acceptance fixes count against the same cap.

xref:recipe-author/harness.adoc#limits[Time and attempt limits] explains which results use up an attempt.
When the agent uses up its attempts, or a call of the agent exits with a non-zero code or reports a failure in its event stream and leaves no acceptable change, the run stops with exit 5.
Once the fixes have reached the cap, the next failing acceptance check stops the run with exit 5 at once, with `the acceptance check of <patch> fails again after the harness's <n> fixes`.
Either stop with exit 5 writes a handoff for each failing acceptance check, as a stop with exit 6 does (see <<without-harness>>).
xref:user/stops.adoc#exit-5[Exit 5: the agent gives up] explains how to go on.

A harness command that is not executable counts as no harness.
debaser warns with `warning: harness <executable> is not executable; continuing without it` and goes on as in <<without-harness>>.

xref:recipe-author/harness.adoc[Setting up the harness] shows how to configure the harness and its `tasks`, and xref:recipe-author/harness-verification.adoc[What the agent is asked and how its work is checked] how debaser judges the agent's fix.

[#without-harness]
=== Without a harness

Without a harness, the run stops with exit 6.
In plain output, the stop starts with `debaser stopped: the acceptance check of <patch> fails`, naming the patch of the first failing acceptance check.
Below it, `failing acceptance checks:` lists all failing checks, `command:` gives the check's command, and `log:` its log.

debaser writes a handoff for each failing acceptance check, in the report's `handoffs` directory.
It has the kind `acceptance` and the cause `the build no longer does what this patch is for`.
Its task is to make the check pass again on a build of the patch's branch merged onto the latest upstream.
xref:user/stops.adoc#exit-6[Exit 6: an acceptance check fails] explains how to fix the problem and continue.

=== What a failing check leaves alone

A stop at an acceptance check does not install anything.
The installed artifact and the previous build stay as they were at the start of the run.

In `result.json`, the `checks` field, which covers the recipe steps, stays `pass` for every merged patch at an acceptance stop; only the `acceptance` field records the failure.

== Where debaser shows the checks

`debaser list`::
Adds `(with check)` to the description of each patch with an acceptance check.
With `--json`, each patch has `hasCheck`.

`debaser status`::
The PATCH CHECK column shows the result of each patch's acceptance check in the last build, and `-` for a patch without one.
xref:user/status.adoc#table[The patch table] lists every value.

The build summary::
In plain output, the summary of a successful build has a line `agent fix <commit> for the acceptance check of <patch>` for each agent fix.
A fix that `debaser continue` committed for you shows as `user fix <commit> for the acceptance check of <patch>`.
A flaky acceptance check adds `warning: the acceptance check of <patch> failed once and passed when run again; it may be flaky (<log>)`.

`report.md`::
The section `Acceptance checks` lists each patch with a check and its result, as `- <patch>: <result>`.
Patches without a check do not appear there.
When no patch has a check, the report has no such section.
A flaky check also appears under `Warnings and notes`, and a fix of an acceptance check, by the agent or by you, under `Fix commits` as `acceptance <patch>`.

`result.json`::
Each patch has an `acceptance` field with one of these values:
+
[cols="1,3",options="header"]
|===
|Value |Meaning

|`pass`
|The check passed.

|`flaky`
|The check failed once and passed when debaser ran it again.

|`fixed`
|The check passed after an agent fix for its patch earlier in the run.

|`fail`
|The check failed.

|`not run`
|The patch has a check, but the run ended before it ran.

|`none`
|The patch has no check.

|`skipped`
|The build skipped the patch, or the patch is retired.
|===
