A recipe tells debaser how to check and build a project: named steps run in order, the build output, and where to install it.
debaser ships generic recipes for Bun and TypeScript projects (`bun-ts`) and for Rust projects built with Cargo (`rust-cargo`), plus project recipes for `tals/corgi` and `rtk-ai/rtk`.
When none of them matches your project and no recipe of its own is in place, a build stops with "no recipe matches this project".
This section shows you how to write that recipe, either as a local `recipe.toml` next to your patch list or as a `.debaser/recipe.toml` that the project commits.
With a recipe in place, debaser can check, build, and install the project on every run.

The recipe's checks tell you that the combined build works.
They do not tell you that each patch still does what it is for.
An acceptance check covers that gap: a command you attach to one patch in `patches.json`, which debaser runs after every recipe step has passed.

Without an agent, a merge conflict or a failing check stops the build until you fix it.
A harness hands that work to a coding agent, a command-line program that changes code from a written task (Claude Code, Codex, pi, OpenCode, or any command you name).
You configure the harness in the `harness` section of `patches.json`.
debaser checks the agent's result itself before it keeps it.
It commits an accepted fix as a separate commit, and records an accepted conflict resolution in the patch's merge commit.
When the agent cannot finish the job, the run stops with exit 5, and you can fix the problem yourself and run `debaser continue`.

xref:overview/concepts.adoc[Key concepts] defines the terms these pages use.
The reference pages xref:reference/recipe-toml.adoc[Recipe file] and xref:reference/patches-json.adoc[`patches.json`] list every key.
