A recipe tells debaser how to check, build, and install a project.
It is a TOML file with named recipe steps that debaser runs in order.
It can name an xref:recipe-author/steps.adoc#the-install-step[install step] and the files that trigger it.
It can also set the build output, the path of the installed artifact, a command to run after the build, and overrides for the prompts an agent gets.
Two more keys set the project's name (`project_name`) and globs for temporary files the build leaves behind (`leftovers`).
debaser never commits those files when it commits a fix.
debaser rejects a recipe with a key it does not know, and the message names the file and the key.

debaser assembles the effective recipe from up to four layers, each extending the one below it.
To change what a build does, you add a layer: a xref:recipe-author/steps.adoc#write-a-local-recipe[local recipe] for your clone, or a recipe the project commits.
xref:recipe-author/steps.adoc[Steps, install, and build output] covers the keys of a single step and how you place new steps.

[#the-four-layers]
== The four layers

From the bottom up, the layers are:

generic recipe::
A recipe for a type of project, such as Bun and TypeScript or Rust with Cargo.
debaser picks one, if any, as described in <<generic,How debaser chooses the generic recipe>>.
In `debaser recipe` output, the `LAYER` column shows it as `generic:<name>`.

built-in project recipe::
A recipe for one upstream repository.
debaser uses it when the patch list's `upstream.repo` matches the recipe's `owner/repo`, regardless of case.
In `debaser recipe` output, the `LAYER` column shows it as `project:<owner>/<repo>`.

the project's recipe::
The file `.debaser/recipe.toml` that the upstream project commits.
debaser reads this file from the fetched upstream commit, never from a patch or the merged result.
It uses the file only after you trust it (see <<trust,Trust the project's recipe>>).
In `debaser recipe` output, the `LAYER` column shows it as `repo:.debaser/recipe.toml@<commit>`.

local recipe::
The file `recipe.toml` in the xref:overview/concepts.adoc#data-directory[data directory], next to `patches.json`.
By default the data directory is `debaser` inside your clone's shared Git directory; `--dir` or `DEBASER_DIR` moves it.
In `debaser recipe` output, the `LAYER` column shows this layer as `local`.

Any layer can be missing.
Where two layers set the same key or the same step, the higher layer applies: the project's recipe, once trusted, over a built-in project recipe, and the local recipe over both.
Only the `leftovers` lists combine across layers.

=== How a layer extends the one below

debaser merges the present layers from the bottom up.
For each key, a higher layer changes the result in one of these ways:

* `steps`: a step with the name of a lower layer's step replaces that step at its place in the order.
The higher layer's step replaces the lower one as a whole, so the lower step's `parser`, `timeout`, or `tests` do not carry over.
A `before` or `after` key on such a step has no effect.
A step with a new name goes where its `before` or `after` key places it, or at the end if it sets neither.
That key must name a step from a lower layer or an earlier step of the same layer.
Otherwise debaser stops with `step <name> is placed before <other>, which no lower layer has` (or `after`).
`steps_replace = true` drops the steps of all lower layers first.
* `install` and `artifact`: each key (`install.step`, `install.triggers`, `install.marker`, `artifact.output`, `artifact.install`) replaces the lower layer's value on its own, and the keys a layer leaves out stay as they were.
* `project_name`, `after_build`, and each entry under `prompts`: the higher layer's value replaces the lower one.
* `leftovers`: the lists of all layers combine.

After the merge, the recipe needs at least one step, and `install.step` must name one of the steps.
Otherwise debaser stops with `the recipe has no steps` or `the install step <name> is not one of the recipe's steps`.
An `[install]` table for which no layer sets `step` stops it with `the recipe's [install] table names no step`.

When no layer sets `project_name`, debaser uses the repository part of the patch list's `upstream.repo`.

[#generic]
== How debaser chooses the generic recipe

debaser takes the first of these that names a generic recipe:

. `recipe` in `patches.json`.
. `recipe` in the local `recipe.toml`.
. `extends` in the lowest non-generic layer present.
. Detection: each generic recipe lists file names under `detect`, and debaser looks for them at the fetched upstream commit.
If upstream has not been fetched yet, debaser looks in the working tree it runs in.

Only the lowest non-generic layer present may set `extends`.
In a higher layer, debaser stops with `<layer>: extends is only allowed in the lowest non-generic layer (<lowest layer>)`.

When debaser finds no generic recipe, it still builds as long as another layer exists, and the effective recipe has no generic layer.
The following cases stop the command with exit 1.
In a build, debaser stops before it merges any patch.

[cols="1,2",options="header"]
|===
|Case |Message

|`recipe` or `extends` names a generic recipe debaser does not have
|`no generic recipe named <name>; debaser has bun-ts, rust-cargo`

|Detection finds more than one generic recipe
|`several generic recipes match this project: <names>; name one with "recipe" in the patch list`

|Detection finds none, and no other layer exists
|`no recipe matches this project; debaser has bun-ts, rust-cargo`, followed by `name one with "recipe" in the patch list, or write a local recipe.toml beside it`
|===

== The built-in recipes

The built-in recipes are part of the debaser binary, and debaser never fetches them.
A built-in recipe whose `name` has the form `owner/repo` is a project recipe; any other is a generic recipe.

[cols="1,1,3",options="header"]
|===
|Recipe |Kind |What it sets

|`bun-ts`
|generic, detected by `bun.lock` or `bun.lockb`
a|
* Steps:
** `install`: `bun install --frozen-lockfile`
** `typecheck`: `bunx tsc --noEmit`, parser `tsc`
** `test`: `+bun test {tests}+`, parser `bun-test`
* Install step `install`, triggered by `bun.lock` and `package.json`, with the marker `node_modules`
* No build output and no install path

|`rust-cargo`
|generic, detected by `Cargo.toml`
a|
* Steps:
** `fetch`: `cargo fetch --locked`
** `test`: `cargo test`, parser `cargo-test`
** `build`: `cargo build --release`
* Install step `fetch`, triggered by `Cargo.lock` and `Cargo.toml`
* No build output and no install path

|`tals/corgi`
|project, extends `bun-ts`
a|
* Replaces `typecheck` with `bun typecheck.ts`, parser `tsc`
* Adds `native` (`bun build.ts --native-only`) before `test`, because the unit tests need the native layer built first
* Replaces `test` with `+bun test {tests} --timeout 60000+`, parser `bun-test`, and limits `+{tests}+` to `src`
* Adds `build` (`+bun build.ts --outfile {output}+`) at the end
* Build output `dist/corgi-debaser`, installed at `dist/corgi-custom`
* After-build command `./dist/corgi-custom reload`
* Project name `corgi`

|`rtk-ai/rtk`
|project, extends `rust-cargo`
a|
* Adds `fmt` (`cargo fmt --check`) and `clippy` (`cargo clippy --all-targets -- -D warnings`) before `test`
* Build output `target/release/rtk`, installed at `dist/rtk-custom`
* Project name `rtk`
|===

xref:reference/recipe-toml.adoc[Recipe file] lists every key of a recipe with its merge rule.

[#trust]
== Trust the project's recipe

A recipe runs commands on your machine.
debaser runs the commands of the project's recipe only after you trust that recipe.

debaser records the trust per upstream repository in `trust.json` in the data directory, together with a SHA-256 fingerprint.
The fingerprint covers the recipe file and the prompt files it names (`.md` paths, read from `.debaser/` at the same upstream commit).
A change to the recipe or to one of those prompt files changes the fingerprint, and debaser asks again.

When a run reads the project's recipe and that recipe is not trusted yet or has changed since you trusted it, debaser does one of the following:

* With `--trust-recipe`, it trusts the recipe, records the trust, and prints `trusting .debaser/recipe.toml at <commit> (--trust-recipe)` as a progress line.
* On a terminal, it lists each step with its command.
It adds the after-build command, install path, and prompt files when the recipe sets them, then asks `Trust it? [y/N]`.
Control characters and bidirectional text markers in the commands appear as `\u` escapes.
`y` or `yes` records the trust; any other answer stops the run with `the project's recipe .debaser/recipe.toml was not trusted; nothing was changed`.
* Without a terminal, it stops with exit 1: `the project's recipe .debaser/recipe.toml at <commit> is not trusted yet` (or `changed since you trusted it`), followed by `+review it, then run `debaser trust`, or pass --trust-recipe+`.

xref:user/headless.adoc#trust-the-projects-recipe[Running headless] explains which commands accept `--trust-recipe` and what it means for a scheduled job.

`debaser trust` reviews the recipe before a build, so the build does not stop at the question.

. In your clone, on a terminal, run `debaser trust`.
It fetches the upstream branch and reads `.debaser/recipe.toml` at its tip.
When the recipe is not trusted yet, it shows what the recipe runs and asks `Trust it? [y/N]`.
Answer `y` after you have read the commands.
+
Check: debaser reports the recipe as trusted, as already trusted, or says the project has no recipe to trust.
+
[source,bash]
----
debaser trust
----
// expect: exit 0 and matches /debaser: trusted|already trusted|nothing to trust/

. Show the effective recipe.
+
Check: the output has no note that `.debaser/recipe.toml` is not trusted.
+
[source,bash]
----
debaser recipe
----
// expect: exit 0 and not-contains "is not trusted"

When the recipe is not trusted yet, or changed since you trusted it, `debaser trust` needs a terminal for its question.
Without one, it stops with exit 1 and `trusting a recipe needs a terminal to confirm on`.
Any answer other than `y` or `yes` stops it with `.debaser/recipe.toml was not trusted`.

[#see-the-effective-recipe]
== See the effective recipe

`debaser recipe` shows the recipe a build would use and the layer each value comes from.
Run it after you add or change a layer, to see what your change did before a build runs it.

The command only reads.
It does not fetch: it uses the upstream commit you fetched last.
It leaves an untrusted `.debaser/recipe.toml` out without asking, and adds the note `+.debaser/recipe.toml at <commit> is not trusted and not used; `debaser trust` reviews it+`.

The output has three parts:

* A line that names the layers from the bottom up, separated by `<`.
The layers line shows a built-in layer as its layer ID followed by `(built-in)`, for example `generic:bun-ts (built-in)`.
It shows the project's recipe as `repo .debaser/recipe.toml at upstream <commit>` and the local recipe as `local <path>`.
* A table of the steps in order, with the columns `STEP`, `COMMAND`, `PARSER`, and `LAYER`.
The `COMMAND` column also shows the step's `+{tests}+` list and its timeout when the step sets them.
* A table with the columns `VALUE`, `SETTING`, and `LAYER` for `project_name`, the `install` and `artifact` keys, `after_build`, `leftovers`, and each overridden prompt.
For a `project_name` that no layer sets, the `LAYER` column says `default`.

`debaser recipe --json` prints the effective recipe as JSON, with the layer of each step and an `untrustedRepoRecipe` field.

. Fetch upstream, so that the project's recipe and the generic recipe detection read the latest upstream commit.
Use the name of your upstream remote if it is not `upstream`.
+
[source,bash]
----
git fetch upstream
----

. Show the effective recipe.
+
Check: debaser prints the table of steps, each with the layer it comes from.
+
[source,bash]
----
debaser recipe
----
// expect: exit 0 and contains "STEP"
