You build debaser from source on your own machine.
This guide was verified against one debaser commit, called the verified commit on this page.
That commit has no release workflow, only a CI workflow that tests and builds, so there is no release binary to download.
The build compiles debaser into a single executable, `dist/debaser`, which you then copy onto your `PATH`.
This page installs debaser version {debaser-version}.

== What you need

Git {debaser-git-min} or newer::
debaser needs Git at run time.
The commands that change something (`add`, `remove`, `build`, `rebase`, `continue`, `rollback`, and `trust`) check the Git version when they start.
With an older Git, they stop with the message `git {debaser-git-min} or newer is required`, followed by the version they found.

Bun::
Bun compiles debaser's TypeScript source into the executable (`bun build --compile`).
You need it only for the build, not to run debaser.
The project's CI builds and tests debaser with Bun {debaser-bun-tested} on `ubuntu-latest` and `macos-latest` runners (link:{debaser-blob}/.github/workflows/ci.yml#L22-L29[CI workflow]).
The README at the verified commit asks for a lower minimum, but CI tests only this version.

[[gh]]GitHub CLI (`gh`), optional::
debaser looks for `gh` on your `PATH` and runs it to ask GitHub about a pull request: its state, title, body, merge commit, and head branch.
debaser fetches and merges pull requests with Git, so they build without `gh` too.
Without `gh`, or when `gh` cannot answer (not signed in, offline), debaser behaves differently in these ways, among others:
+
* The pull request's state and title are unknown, and the run's summary and report carry a warning about it.
* debaser cannot see that upstream merged a pull request by squash or rebase, so it merges that pull request again.
It skips the pull request only when upstream contains its original commits.
* `debaser add` cannot take a pull request's title as its description, so you give one yourself: `debaser add <number> "<description>"`, where `<number>` is the pull request's number.
* debaser cannot tell whether a pull request comes from a branch of your own fork, so it does not rebase that branch.

Coding agents, optional::
A coding agent is a command-line program that changes code from a written task.
debaser can hand it a merge conflict, a failing recipe step, or a failing acceptance check.
debaser runs the agent through a harness, which you configure in the `harness` section of `patches.json`.
The harness can run Claude Code (`claude`), Codex (`codex`), pi (`pi`), OpenCode (`opencode`), or any other command.
Without a harness, each of these problems stops the run, and you fix it yourself.
xref:overview/how-it-works.adoc[How a build works] lists each stop and its exit code, and xref:overview/concepts.adoc[Key concepts] defines recipe steps, acceptance checks, and the harness.

== Build and install debaser

Install Git and Bun before you start.
The steps clone debaser at the verified commit, so the executable you build matches these pages.

. Check your Git version.
+
Check: the output starts with `git version`, followed by version {debaser-git-min} or newer.
+
[source,bash]
----
git --version
----
// expect: contains "git version"

. Clone the debaser repository and check out the verified commit.
+
[source,bash,subs="attributes+"]
----
git clone {debaser-repo}
cd debaser
git checkout {debaser-commit}
----
+
Git reports a detached `HEAD`, which is expected: you build from a fixed commit, not from a branch.
+
Check: `HEAD` is at the verified commit, `{debaser-commit}`.
+
[source,bash,subs="attributes+"]
----
git rev-parse HEAD
----
// expect: contains "{debaser-commit}"

. Install the build dependencies.
+
[source,bash]
----
bun install
----

. Build the executable.
+
[source,bash]
----
bun run build
----
+
The `build` script compiles debaser into one file, `dist/debaser`.

. Copy `dist/debaser` to a directory on your `PATH`.
The commands below use `~/.local/bin` and create it if it does not exist.
If that directory is not on your `PATH`, use a directory that is.
+
[source,bash]
----
mkdir -p ~/.local/bin
cp dist/debaser ~/.local/bin/
----

. Confirm that your shell finds the new executable.
`debaser --version` works in any directory, even outside a Git repository.
+
Check: debaser prints `debaser {debaser-version}`.
+
[source,bash,subs="attributes+"]
----
debaser --version
----
// expect: contains "{debaser-version}"

Next, set up your clone of the project you want to patch and run your first build: xref:user/first-build.adoc[Your first build].
