A build checks out the integration branch, resets it to upstream, and merges your patches onto it.
debaser does that work in the build directory, a linked Git worktree of your clone that holds the integration branch.
Unless that checkout is the build directory, as when you build in place, the checkout you start debaser from stays as it is.
You can keep editing, switch branches, or run a dev server there while a build runs.

This page shows where the build directory lives, how to move it or build in place, which commands use it, and what to do when debaser refuses to use it.
xref:overview/concepts.adoc[Key concepts] defines the terms, and xref:user/first-build.adoc[Your first build] creates the build directory for the first time.

== Where the build directory lives

By default the build directory sits beside the main checkout as `../<clone>-debaser`, where `<clone>` is the name of the main checkout's directory.
The main checkout is the first worktree that `git worktree list` shows, usually the directory you cloned into.
debaser resolves the default against the main checkout, also when you start it from a linked worktree or keep the data directory outside the repository with `--dir` or `DEBASER_DIR`.

The first build that creates the directory records it in the patch list as a relative path, for example `"tree": "../widget-debaser"` for a clone named `widget`.
`debaser rollback` without a stopped run checks and creates the build directory the same way, so it can record `tree` too.

image::where-things-live.svg["Your clone with its shared Git directory, which holds debaser's data directory, the fetched refs, and the branches; the build directory beside it as a linked worktree on the integration branch, with the build output, the installed artifact, and its .prev copy; and the remotes upstream and origin",role=expand]

The diagram shows the default layout.
The build directory is a linked worktree added from your clone, so it shares the clone's Git directory, and with it the data directory, the patch list, and the branches.
It holds the recipe's build output (`artifact.output`), the installed artifact (`artifact.install`), and the `.prev` copy of the installed artifact from the start of the run.
Two settings change that picture.
With `"tree": "."`, the build directory is the main checkout itself, and those files land there.
When the recipe gives an absolute `artifact.install` or `artifact.output` path, debaser uses that path as it is, outside the build directory.

=== The `tree` setting

`tree` in `patches.json` names the build directory.
debaser accepts any non-empty string and keeps the value as written.

* A relative path counts from the main checkout, for example `"tree": "../widget-build"`.
* An absolute path is used as it is.
* `"tree": "."` names the main checkout itself, so debaser builds in place.

debaser has no command that sets `tree`.
You edit `patches.json` by hand, as xref:user/patch-list.adoc#edit-by-hand[Managing the patch list] describes, and `debaser list` names the file on its `config` line.

=== What `list` and `status` show

`debaser list` and `debaser status` start with three lines: the data directory (`data`), the patch list (`config`), and the build directory (`build`).
When the build directory needs attention, the `build` line adds a note in parentheses.

[cols="1,2"]
|===
|Note |Meaning

|`not created yet`
|No `tree` is recorded and nothing exists at the default path.
The next build creates it.

|`missing`
|A `tree` is recorded, but the directory is gone.
The next build creates it again.

|`in place`
|`tree` names the main checkout.
With modified tracked files, the note adds their number, as in `in place, 2 modified files`.

|`not a worktree of this repository`
|The path exists, but it is not the top level of a worktree of this clone.

|`on <branch>, not <integration branch>`
|The build directory has another branch checked out.

|`on a detached HEAD, not <integration branch>`
|The build directory has no branch checked out, and the integration branch exists.

|`<n> modified files`
|The build directory has modified tracked files (`1 modified file` for one).
|===

The notes in the last four rows match refusals described in <<refusals>>.

== Which commands use it

`debaser build`, `debaser continue`, and `debaser rollback` work in the build directory, wherever you start them.

* `debaser build` checks the build directory, creates it when it is missing, and names it at the start of the run.
That line appears in the plain progress lines, and in the live view only with `--verbose`.
* `debaser continue` goes on in the build directory of the stopped run.
* `debaser rollback` undoes a stopped run in that run's build directory.
Without a stopped run, it restores the previous build there and runs the same checks as a build first.

When a build stops, the stop lines name the build directory on a `build directory:` line.
Resolve the conflict or fix the step there, then run `debaser continue` from any worktree of the clone.

`debaser rebase` does not use the build directory.
It works from the checkout you start it from and rebases your own branches in throwaway worktrees, or with `--in-worktree` in the worktree that has the branch checked out.
Its handoffs name the build directory as `none (a rebase run)`.
`debaser continue` and `debaser rollback` of a stopped rebase run do not use the build directory either.

== Working beside a build

A build leaves the checkout you start it from alone, unless `tree` names that checkout or you pass `--in-worktree` (see below).
A build started in a main checkout with uncommitted edits on a feature branch leaves both the branch and the edits as they were.
A build started from the build directory itself, or from a third worktree, builds in the same build directory.

Own branches are a special case.
When one of your own branches needs a rebase and is checked out in a worktree, for example your main checkout, a build reports it as checked out there and leaves it alone.
With `--in-worktree`, the build rebases it in that worktree instead.
xref:user/own-branches.adoc[Rebasing your own branches] covers the details.

In a new or recreated build directory, the recipe's install step has not run yet.
When the recipe's `install` section names an install step, the first build there runs it.
When that section also names trigger files, later builds run the step again only when one of them changed.

[#move]
== Move the build directory

You might want the build directory on another disk or under another name.
A build refuses while the integration branch is checked out in a worktree other than the build directory, and the old build directory has it checked out.
So remove the old build directory before you point `tree` at the new place.

[CAUTION]
====
With relative `artifact` paths, the installed artifact and its `.prev` copy live in the build directory.
Removing the old build directory deletes them with it.
The next build installs the artifact again in the new place.
====

. Show where the build directory is now.
+
Check: the `build` line names the current build directory.
+
[source,bash]
----
debaser list
----
// expect: matches /(^|\n)build +\S/

. Remove the old build directory with Git.
`<old path>` is the path from the `build` line.
+
[source,bash]
----
git worktree remove <old path>
----
+
Check: the list of worktrees no longer contains the old path.
+
[source,bash]
----
git worktree list
----
// expect: not-contains "-debaser"

. Open `patches.json` and set `tree` to the new place, relative to the main checkout or absolute.
+
[source,json]
----
"tree": "<new path>"
----

. Run a build.
It creates the new build directory from the existing integration branch.
+
[source,bash]
----
debaser build
----

. Confirm that the new build directory holds the integration branch.
+
Check: the list of worktrees contains `<new path>` with the integration branch in brackets, `[debaser]` for the default name.
+
[source,bash]
----
git worktree list
----
// expect: contains "[debaser]"

The `not-contains "-debaser"` expectation in step 2 fits the default name; with your own `tree`, look for your old path instead.

== Build in place

Building in place puts the integration branch into the main checkout itself.
It suits a CI job with a single checkout.
In place, debaser skips the check for another branch or a detached HEAD.
The check for modified tracked files still applies.
If you already built, the existing build directory still has the integration branch checked out, and the build would refuse.
Remove it first, as steps 1 and 2 of <<move>> show.

[WARNING]
====
A build in place switches the main checkout to the integration branch and resets that branch to upstream.
After the build, the branch you had checked out there is no longer checked out.
====

. Remove an existing build directory, if there is one, as in <<move>>.
Skip this step before your first build.

. Open `patches.json` and set `tree` to the main checkout.
+
[source,json]
----
"tree": "."
----

. Make sure the main checkout has no modified tracked files.
Untracked files do not count.
+
Check: the command prints nothing.
+
[source,bash]
----
git status --porcelain --untracked-files=no
----
// expect: lines == 0

. Run the build.
+
[source,bash]
----
debaser build
----

. Confirm the branch of the main checkout.
+
Check: the main checkout has the integration branch checked out, `debaser` for the default name.
+
[source,bash]
----
git branch --show-current
----
// expect: contains "debaser"

If you later remove `"tree": "."` again, the main checkout still has the integration branch checked out, and the next build refuses until you switch it away (see <<held-by-main>>).

[#refusals]
== When debaser refuses the build directory

Before a build changes anything, debaser checks the build directory.
A refusal ends the command with exit 1 and leaves everything as it was, the patch list included.
In plain output, the message is a single line that starts with `debaser:`.
The sections below quote each message, with `<path>`, `<branch>`, and the other placeholders standing for the values debaser fills in.

=== Modified tracked files

debaser refuses when the build directory has staged or unstaged changes to tracked files.
It lists up to ten of them, then the number of the rest.

[source,text]
----
debaser: the build directory <path> has uncommitted changes in: <files>; commit, stash or discard them first
----

Commit, stash, or discard the changes in the build directory, as the message says.
Each build resets the integration branch to upstream.
Untracked files never block a build.

This check applies only when no run is stopped.
`debaser rollback` of a stopped run discards the run's changes in the build directory, because they belong to the run.

=== Another branch or a detached HEAD

debaser refuses when the build directory has a branch other than the integration branch checked out.
It refuses a detached HEAD too, once the integration branch exists.
Before that, a detached build directory is the state in which debaser creates it from upstream.

[source,text]
----
debaser: the build directory <path> has <branch> checked out, not <integration branch>; switch it back first, or set another path as "tree" in <patch list>
debaser: the build directory <path> has a detached HEAD checked out, not <integration branch>; switch it back first, or set another path as "tree" in <patch list>
----

Switch the build directory back to the integration branch with `git switch`:

[source,bash]
----
git -C <path> switch <integration branch>
----

Or point `tree` at another place, as the message offers.

Two data directories that use the default `tree` share one build directory.
When their patch lists name different integration branches, the first build of the second patch list refuses with this message.
Give the second patch list its own `tree`.

=== Not a worktree of this repository

debaser refuses a path that exists but is not the top level of a worktree of this clone.
A plain directory, a subdirectory of a worktree, or a checkout of another repository at that path all count.
debaser never writes into such a directory.

[source,text]
----
debaser: <path> is not a worktree of this repository; set another path as "tree" in <patch list>
----

Set another path as `tree` in the patch list.
When the directory sits at the default path and no `tree` is recorded yet, setting `tree` is the way out too.

[#held-by-main]
=== The integration branch checked out in the main checkout

debaser refuses when the main checkout has the integration branch checked out and the build directory is elsewhere.
That happens, for example, after you built in place and then removed `"tree": "."`.
The message gives the command that fixes it.

[source,text]
----
debaser: the main checkout (<main checkout>) has <integration branch> checked out; switch it away first: git -C <main checkout> switch <upstream branch>
----

Run the command from the message, which switches the main checkout to the upstream branch:

[source,bash]
----
git -C <main checkout> switch <upstream branch>
----

Check: the main checkout no longer has the integration branch checked out.

[source,bash]
----
git -C <main checkout> branch --show-current
----
// expect: not-contains "debaser"

The expectation fits the default integration branch name, `debaser`.

=== The integration branch checked out in another worktree

debaser refuses when any other worktree of the clone has the integration branch checked out, and names that worktree.
The check also counts a registered worktree whose directory is gone.

[source,text]
----
debaser: <integration branch> is checked out in another worktree (<worktree>); switch it away first
----

When that worktree's directory exists, switch it to another branch:

[source,bash]
----
git -C <worktree> switch <other branch>
----

For a registration whose directory is gone, the switch cannot run: such a registration stays until it is pruned, so prune it.

[source,bash]
----
git worktree prune
----

=== Checks before a rollback of a stopped run

`debaser rollback` of a stopped run checks the run's build directory with its own rules.
It refuses when the integration branch is checked out in another worktree, with the messages above.
It refuses when the build directory has another branch or a detached HEAD checked out, with the same message as a build, unless the run built in place.
When the build directory is on another branch or a detached HEAD with uncommitted changes, it refuses first, because a rollback would discard them:

[source,text]
----
debaser: <branch> has uncommitted changes, and rollback would discard them; commit or stash them first
debaser: the detached HEAD has uncommitted changes, and rollback would discard them; commit or stash them first
----

When the run's build directory is no longer a worktree of this clone, `debaser continue` and `debaser rollback` both refuse:

[source,text]
----
debaser: <path> is no longer a worktree of this repository; move it away, then undo the run with `debaser rollback`
----

Move the directory away, then run `debaser rollback`.

== A deleted build directory

debaser never deletes the build directory.
When you delete it by hand, the next build creates it again at the same path.
It first drops the stale Git registration of that one directory, then adds the worktree from the integration branch.
In plain output, the progress line says so:

[source,text]
----
debaser: creating the build directory <path> from <integration branch> (it was missing)
----

A locked worktree that is not there is a different case.
debaser keeps the lock, because a locked worktree may sit on a volume that is away on purpose, and refuses:

[source,text]
----
debaser: the build directory <path> is a locked worktree that is not there; bring it back, or unlock it: git worktree unlock <path>
----

Bring the volume back, or unlock the worktree with the command from the message.

When the build directory disappears while a run is stopped, `debaser continue` refuses and points at rollback:

[source,text]
----
debaser: the build directory <path> is gone; undo the run with `debaser rollback`
----

`debaser rollback` then moves only the refs back: the integration branch returns to where it stood before the run, or is deleted when there was no build before.
It prints that the next build creates the build directory again.

A run stopped by a debaser version that recorded no build directory continues and rolls back in the worktree that has the integration branch checked out.
When no worktree has it checked out, both commands refuse with `no worktree has <integration branch> checked out; check it out again where the run was started`.
