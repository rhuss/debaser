This page takes you from a plain clone of a project to its first patched build.
You give the clone an `upstream` remote for the original repository, add your first patches to the patch list, and build once.
When upstream moves later, you run the same build command again to refresh the build.

The steps use placeholders for your own values.
`<owner>/<repo>` is the original GitHub repository, and `<you>` is your GitHub account.
`<number>` is the number of a pull request on upstream, `<branch>` is a branch name, and `<fork-owner>/<fork-repo>` is another GitHub repository with a branch you want, for example someone else's fork.
You need debaser on your `PATH` (xref:user/install.adoc[Install debaser]).
xref:overview/concepts.adoc[Key concepts] defines the terms this page uses.

[#set-up-the-clone]
== Set up the clone

debaser reads the upstream repository from a remote named `upstream` when it creates the patch list.
Your fork stays `origin`, the remote you push to.
If your clone cannot have an `upstream` remote, read <<no-upstream-remote>> before you add patches.

. Clone your fork of the project and change into the clone.
Skip this step when you already have a clone.
+
[source,bash]
----
git clone https://github.com/<you>/<repo>.git
cd <repo>
----

. Add the original repository as the remote `upstream`.
+
[source,bash]
----
git remote add upstream https://github.com/<owner>/<repo>.git
----
+
Check: the list of remotes contains `upstream` next to `origin`.
+
[source,bash]
----
git remote -v
----
// expect: contains "upstream"

. Fetch upstream.
`debaser recipe` in a later step reads the project's files at the fetched upstream commit.
+
[source,bash]
----
git fetch upstream
----

== Add your first patches

The first `debaser add` creates the patch list, `patches.json` in debaser's data directory, which by default lives in the clone's shared Git directory.
It takes the upstream repository, `<owner>/<repo>`, from the URL of the `upstream` remote, and the upstream branch from that remote's default branch.
The integration branch, the branch debaser builds, is `debaser`.
Every later `debaser add` appends a patch at the end of the list, and debaser merges the patches in the order of the list.

. Add a pull request of upstream by its number.
debaser asks the GitHub CLI (`gh`) for the pull request's title, removes a leading area prefix such as `docs:`, and uses the rest as the patch's description.
+
Check: debaser confirms the new patch with a line that starts with `added <owner>/<repo>#<number>:`, followed by its description.
+
[source,bash]
----
debaser add <number>
----
// expect: contains "added"
+
Without `gh`, or when `gh` cannot answer, debaser has no title to take, so the command stops with exit 1 and shows how to pass a description.
Give the description as the second argument:
+
[source,bash]
----
debaser add <number> "<description>"
----
+
xref:user/install.adoc[Install debaser] lists what else changes without `gh`.

. Add one of your own branches.
Without a description, the branch's name becomes its description.
debaser refuses the integration branch (`debaser`) and the previous build's branch (`debaser-prev`) as patch branches, because it resets both on every run.
+
Check: debaser confirms the new patch as `added <branch>: <branch>`.
+
[source,bash]
----
debaser add <branch>
----
// expect: contains "added"

. Add a branch of another repository, as `<fork-owner>/<fork-repo>:<branch>`.
For a repository outside GitHub, give its Git URL as `<git url>#branch=<branch>`.
Without a description, the branch's name becomes its description.
+
Check: debaser confirms the new patch as `added <fork-owner>/<fork-repo>:<branch>: <branch>`.
+
[source,bash]
----
debaser add <fork-owner>/<fork-repo>:<branch>
----
// expect: contains "added"

. Show the patch list.
The output starts with three lines: the data directory (`data`), the patch list file (`config`), and the build directory (`build`), which is marked as not created yet before the first build.
The patches follow in the order debaser merges them.
+
Check: the `config` line names the patch list, `patches.json`.
+
[source,bash]
----
debaser list
----
// expect: contains "patches.json"

`<number>` and `#<number>` name a pull request on upstream.
`<owner>/<repo>#<number>` or the pull request's URL names one on any GitHub repository.
debaser refuses a source that is already in the list.
xref:user/patch-list.adoc[Managing the patch list] covers every source form and how to change the list.

== Check the recipe

A recipe tells debaser how to check, build, and install the project.
debaser assembles it from layers: a generic recipe for the type of project, a built-in recipe for a known upstream repository, the project's own `.debaser/recipe.toml`, and a local `recipe.toml` in the data directory.
xref:recipe-author/recipes.adoc[Recipes and their layers] explains how the layers combine.

Unless the patch list or a recipe layer names a generic recipe, debaser picks one from the files at the fetched upstream commit.
`bun.lock` or `bun.lockb` selects `bun-ts`, and `Cargo.toml` selects `rust-cargo`.
When no generic recipe matches and no other layer exists, debaser stops with `no recipe matches this project`.
The message suggests naming a generic recipe with `recipe` in the patch list or writing a local `recipe.toml`.
When several generic recipes match, debaser stops and names them.
In a build, both stops end the run with exit 1 before any patch is merged.

. Show the recipe debaser will use.
+
Check: debaser prints a table of the recipe's steps, each with its command and the layer it comes from.
+
[source,bash]
----
debaser recipe
----
// expect: contains "STEP"

`debaser recipe` only reads.
When the project has its own `.debaser/recipe.toml` that you have not trusted, the command leaves it out and says so in a note that points to `debaser trust`.

The project's own recipe runs only after you trust it.
When that recipe at the fetched upstream commit is not trusted yet, or changed since you trusted it, `debaser build` asks on a terminal.
It shows what the recipe runs and installs, followed by `Trust it? [y/N]`.
Any answer other than `y` or `yes` stops the build with nothing changed.
`--trust-recipe` trusts the recipe without the question and records the trust for later runs.
Without a terminal to ask on and without `--trust-recipe`, the build refuses with exit 1.
xref:recipe-author/recipes.adoc[Recipes and their layers] covers trust in detail.

== Run the build

`debaser build` fetches upstream and your patches, rebases your own branches, and merges the patches onto the integration branch.
Then it runs the recipe's steps and the acceptance checks, and installs the build output.
xref:overview/how-it-works.adoc[How a build works] follows each phase.

The first build also creates the build directory, a linked Git worktree beside your clone, and records its place in the patch list as `tree`.
Its default name is `../<clone>-debaser`, where `<clone>` is the name of your clone's directory (`<repo>` after the clone step above).
debaser builds there and leaves the directory you started it from alone.
The recipe's build output and installed artifact live in the build directory, unless the recipe gives absolute paths.

. Run the build.
On a color terminal, debaser shows a live view of the run, a progress card that it redraws in place.
Piped into a file or another program, or with `--json`, it prints plain progress lines instead.
At its start, the build prints a line that names the build directory and the patch list it uses.
The plain progress lines always include it; the live view shows it only with `--verbose`.
+
Check: the build finishes with exit 0, and its summary names what was `built`: the installed artifact's path relative to the build directory, or the integration branch when the recipe installs nothing.
+
[source,bash]
----
debaser build
----
// expect: exit 0 and contains "built "

. Confirm that the build directory exists beside your clone.
+
Check: the list of worktrees contains the build directory, `../<clone>-debaser`, on the integration branch `debaser`.
+
[source,bash]
----
git worktree list
----
// expect: contains "-debaser"

. Confirm that the installed artifact exists.
If `artifact.install` is a relative path, `<install>` is that value, relative to the build directory.
If it is absolute, run `ls` on that path itself.
If `debaser recipe` shows no `artifact.install`, as with the generic recipes, skip this step.
+
Check: the file exists.
+
[source,bash]
----
ls ../<clone>-debaser/<install>
----
// expect: exit 0

== Check the result

`debaser status` shows where debaser keeps its files and how each patch stands against upstream.
It only reads, and it fetches nothing unless you pass `--fetch`.

. Show the status.
+
Check: the first lines name the data directory, the patch list, and the build directory, and the status line below them says that no run is in progress.
+
[source,bash]
----
debaser status
----
// expect: contains "no run in progress"

xref:user/status.adoc[Reading status] explains the patch table.
From here, xref:user/patch-list.adoc[Managing the patch list] shows how to grow the list, and xref:user/build-directory.adoc[The build directory] shows how to move the build directory.

[#no-upstream-remote]
== Clones without an upstream remote

Without an `upstream` remote and without the `--upstream` option, the first `debaser add` refuses with exit 1 and creates nothing.
It names the two ways out:

[source,text]
----
debaser: there is no upstream remote to take the upstream repository from
  add it: git remote add upstream https://github.com/<owner>/<repo>.git
  or name it: debaser add <source> --upstream <owner>/<repo>
----

The first way is the second step of <<set-up-the-clone>>.
The second way names the upstream repository on the command line, in the form `<owner>/<repo>`:

[source,bash]
----
debaser add <number> --upstream <owner>/<repo>
----

With `--upstream` and no `upstream` remote, debaser records `main` as the upstream branch.
When it builds, it fetches that branch and upstream's pull requests from `origin`, so the clone needs an `origin` remote.

[WARNING]
====
When `origin` is your fork, `--upstream` makes debaser fetch the upstream branch and upstream's pull requests from your fork, not from the original repository.
`--upstream` fits a clone whose `origin` fetches from the original repository, for example a clone of upstream itself.
With a fork as `origin`, add the `upstream` remote instead.
====
