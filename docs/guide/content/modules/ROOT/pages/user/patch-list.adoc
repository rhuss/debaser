The patch list is the ordered list of patches that debaser merges onto upstream, kept in `patches.json`.
This page shows how to grow it, hold a patch at one commit, retire a patch, read the list, and edit the file directly.
xref:overview/concepts.adoc[Key concepts] defines the three kinds of patch and what makes a patch yours.
xref:user/first-build.adoc[Your first build] creates the list with the first `debaser add`.

The commands use placeholders for your own values.
`<owner>/<repo>` is a GitHub repository, `<number>` is the number of a pull request, `<branch>` is a branch name, and `<git url>` is the URL of any Git repository.
`<source>` stands for any of the source forms below, and `<sha>` for a commit.

== Source forms

`debaser add` reads its first argument as a pull request, then as a branch of another repository, and otherwise as a branch of your clone.
The first form that fits decides the kind of patch.

[cols="2,1,3"]
|===
|Form |Kind |Names

|`<number>` or `#<number>`
|`pr`
|A pull request on upstream.

|`<owner>/<repo>#<number>`
|`pr`
|A pull request on any GitHub repository.

|`\https://github.com/<owner>/<repo>/pull/<number>`
|`pr`
|The same, by the pull request's URL.

|`<owner>/<repo>:<branch>`
|`fork-branch`
|A branch of another GitHub repository, for example someone else's fork.

|`\https://github.com/<owner>/<repo>/tree/<branch>`
|`fork-branch`
|The same, by the branch's URL on GitHub.

|`<git url>#branch=<branch>`
|`fork-branch`
|A branch of a repository anywhere, by its Git URL.

|`<branch>`
|`branch`
|One of your own branches, the local branch or its copy on `origin`.
|===

Only `\https://github.com/` URLs count as pull request and tree URLs.
An argument that fits none of the other forms is read as a branch name of your clone, and debaser refuses it when Git does not accept it as a branch name.
`debaser add` does not look the branch up.
When the branch exists neither locally nor on `origin`, the next build stops.
With an `origin` remote, the message starts with `cannot fetch origin/<branch> for <branch>`, followed by the reason.
Without one, it is `cannot find <branch>: no such local branch or origin/<branch>`.

[#add-a-patch]
=== Add a patch

Each `debaser add` appends one patch to the end of the list.
`--upstream` counts only on the first `add`, the one that creates the list.

. Add the patch in the form from the table that names it, here a pull request on upstream by its number.
+
Check: debaser confirms the new patch with a line that starts with `added`, followed by the patch's name and its description.
+
[source,bash]
----
debaser add <number>
----
// expect: contains "added "

debaser shows each patch by one name, whatever form you typed: `<owner>/<repo>#<number>` for a pull request, `<owner>/<repo>:<branch>` or `<git url>:<branch>` for a branch of another repository, and the branch name for your own branch.

== Descriptions

Every patch carries a one-line description.
You give it as the second argument or with `--description <text>`; when you give both, `--description` wins.
debaser turns line breaks and runs of spaces into single spaces.

[source,bash]
----
debaser add <number> "<description>"
debaser add <branch> --description "<description>"
----

Without a description, debaser picks one by the kind of patch:

* A pull request takes its title from the GitHub CLI (`gh`), without a leading area prefix such as `docs:`.
* A branch, your own or another repository's, takes the branch name.

Without `gh`, or when `gh` cannot answer, a pull request has no title to take.
`debaser add` then refuses with exit 1 and shows the command with a description to add:

[source,text]
----
debaser: <owner>/<repo>#<number> needs a description (no PR title to take it from): debaser add <owner>/<repo>#<number> "<description>"
----

xref:user/install.adoc[Install debaser] lists what else changes without `gh`.

`--description` is not in the usage text that `debaser --help` prints, but `debaser add` accepts it.

== Refused sources

`debaser add` refuses a source in these cases, with exit 1 and the patch list unchanged.

The source is already in the list::
debaser compares sources by what they name, not by how you typed them.
A pull request counts by its repository in any letter case and its number.
So `<number>`, `#<number>`, `<owner>/<repo>#<number>`, and the pull request's URL name the same patch when `<owner>/<repo>` is upstream.
A branch of another repository counts by the last two parts of the repository's path and the branch, so `<owner>/<repo>:<branch>`, its tree URL, and `\https://github.com/<owner>/<repo>.git#branch=<branch>` name the same patch.
The message is `<name> is already in the list`.
Retired patches do not count, so a source you retired can be added again.

The source is the integration branch or the previous build::
One of your own branches named like the integration branch (default `debaser`) or its backup `<integration branch>-prev` is refused, because debaser resets both on every run.
The message ends with `rename it or set another branch`.
`debaser build` refuses such a patch too, should it get into `patches.json` by an edit.

The URL carries credentials::
A `<git url>#branch=<branch>` source whose URL holds a password, or an `http` or `https` URL with a user name, is refused.
The message says to drop the credentials from the URL and use a Git credential helper.
debaser refuses such a URL in `patches.json` as well.

`debaser add`, `debaser remove`, `debaser build`, `debaser rebase`, `debaser continue`, `debaser rollback`, and `debaser trust` take a lock file in the data directory (see <<where>>).
`debaser add` and `debaser remove` therefore also refuse while another of these commands runs with the same data directory.

[#pin]
== Pin a patch

A pin holds a patch at one commit.
debaser merges exactly that commit, even after the source moves on, and never rebases a pinned patch, not even one of your own branches.
When the source cannot be fetched any more, for example a deleted branch, the build merges the pinned commit and adds a warning to the run.
When the pinned commit is not in your clone, the build tries to fetch it by its id from where the patch comes from (for your own branch, from `origin`; without `origin` it does not try).
If that fails too, the build stops with `cannot find the pinned commit <sha> of <name>`.

. Add the patch with `--pin`.
`<sha>` is any commit your clone knows, which debaser records as its full SHA.
A full 40-character SHA in lowercase hex works even when the commit is not in your clone yet.
+
Check: the confirmation ends with `(pinned at <short sha>)`, the first seven characters of the pinned commit.
+
[source,bash]
----
debaser add <source> --pin <sha>
----
// expect: contains "(pinned at "

Any other value is refused with `--pin needs a commit: <sha> is not one known here (fetch it first)`.

`debaser list` marks a pinned patch with `(pinned <short sha>)` after its description, and `debaser status` adds a column with `pinned <short sha>`.
No command changes or drops the pin of a patch already in the list.
Edit the `pin` entry in `patches.json` for that (see <<edit-by-hand>>).

== Order

debaser merges the patches in the order of the list, the first patch first.
`debaser add` always appends at the end, and no command moves a patch.
To change the order, move the entries within the `patches` array of `patches.json` (see <<edit-by-hand>>).

[#retire]
== Retire a patch

`debaser remove` does not delete a patch.
It moves the patch to the list of retired patches, with the date and your reason, so the list keeps a record of what you dropped and why.

. Retire the patch.
`<source>` may be in any form `debaser add` accepts, as long as it names a patch in the list.
+
Check: debaser confirms with a line that starts with `retired`, followed by the patch's name and the reason.
+
[source,bash]
----
debaser remove <source> --reason "<reason>"
----
// expect: contains "retired "

Without `--reason`, debaser asks `Why is <name> retired?` when its standard input is a terminal.
An empty answer, or no terminal to ask on, ends with `removing <name> needs --reason` and exit 1.
A source that names no patch in the list ends with `<name> is not in the list`.

== Read the list

`debaser list` only reads.
It starts with three lines for the data directory (`data`), the patch list file (`config`), and the build directory (`build`).
Below them, a table shows the patches in merge order with the columns `#`, `PATCH`, `ADDED`, and `DESCRIPTION`.
The description carries `(pinned <short sha>)` for a pinned patch and `(with check)` for a patch with an acceptance check.
On a color terminal, each kind of patch has its own color, and patch names link to the pull request or branch where debaser knows a page for it.

Retired patches are only counted by default, in a line such as `1 retired patch; list --verbose shows them`.
Three options change the output:

`--verbose`::
Lists the retired patches below the live ones, in a table with the columns `PATCH`, `RETIRED`, and `REASON`.

`--retired`::
Shows only the retired patches in that table, or `no retired patches`.
The usage text does not mention `--retired`, but `debaser list` accepts it.

`--json`::
Prints a JSON object on standard output with `config`, `upstream`, `branch`, `patches`, and `retired`.
Each patch is its entry as debaser read it from `patches.json`, plus `display`, the name debaser shows.
Each patch in `patches` also has `hasCheck`, whether it has an acceptance check.
The JSON always holds the retired patches, with or without `--verbose`.
The table still goes to standard error.

. Show the patch list with the retired patches.
+
Check: the table of retired patches follows the live ones when the list has any; otherwise the output matches plain `debaser list`.
+
[source,bash]
----
debaser list --verbose
----
// expect: exit 0

. Read the list as JSON, for a script.
+
Check: standard output holds the JSON object with its `retired` key.
+
[source,bash]
----
debaser list --json 2>/dev/null
----
// expect: exit 0 and contains "retired"

[#where]
== Where the patch list lives

The patch list is `patches.json` in debaser's data directory.
By default that is the directory `debaser` inside the clone's shared Git directory, the one `git rev-parse --git-common-dir` prints.
Every worktree of the clone shares that directory, so the build directory and your clone read the same patch list.

`--dir <path>` or the environment variable `DEBASER_DIR` moves the whole data directory, not only the patch list.
When both are set, `--dir` wins.
A relative path counts from the current directory.
`--dir` may stand before or after the command.

[source,bash]
----
debaser --dir <path> list
DEBASER_DIR=<path> debaser list
----

[WARNING]
====
Each command finds the data directory anew.
A command run without the same `--dir` or `DEBASER_DIR` reads the default data directory, and so another patch list or none.
Without a patch list, `debaser list` and `debaser remove` stop with `there is no patch list yet`.
`debaser add` creates a new one, but only with an `upstream` remote or the `--upstream` option (see xref:user/first-build.adoc#no-upstream-remote[Clones without an upstream remote]).
====

. Show where the patch list is.
+
Check: the `config` line names the file `patches.json`.
+
[source,bash]
----
debaser list
----
// expect: contains "patches.json"

[#edit-by-hand]
== Edit `patches.json` by hand

Some changes have no command.
Among them are the order of the patches, the pin or description of a patch already in the list, removing retired entries, and settings such as the build directory's place (`tree`) or acceptance checks.
For those, edit `patches.json` in a text editor.
xref:reference/patches-json.adoc[`patches.json`] lists every key.

Each patch in the `patches` array is an object like this one, from the fictional project `example/widget`:

[source,json]
----
{
  "source": { "kind": "pr", "repo": "example/widget", "number": 12 },
  "description": "Add a --quiet option",
  "added": "2026-11-23",
  "pin": "<full 40-character commit SHA>"
}
----

`added` is the date `debaser add` recorded, and `pin` is optional.
`source` takes one of three shapes:

* `{ "kind": "pr", "repo": "<owner>/<repo>", "number": <number> }`
* `{ "kind": "fork-branch", "repo": "<owner>/<repo>", "branch": "<branch>" }`, or with `"url": "<git url>"` in place of `repo`
* `{ "kind": "branch", "name": "<branch>" }`

Entries in the `retired` array have the same keys plus `retired`, the date, and `reason`.

debaser reads and checks the file at the start of every command; `--version`, `--help`, `help`, their short forms, a missing command, and an unknown command skip it.
A file that is not valid JSON, or breaks a rule, stops the command with exit 1 and a message that names the file and, for a broken entry, its place, such as `patches[2]`.
Among the rules:

* A description is a single line.
* A pin is a full 40-character commit SHA in lowercase hex.
* A `fork-branch` source has exactly one of `repo` and `url`, and the URL carries no credentials.
* `upstream.repo` has the form `<owner>/<repo>`, and `branch` differs from `upstream.branch`.

`debaser add` and `debaser remove` write the whole file again from what they read.
`debaser build` and `debaser rollback` do the same when they record the build directory's place as `tree`, which happens while the patch list has no `tree` entry, for example on the first build.

[CAUTION]
====
Keep notes for yourself in the descriptions, not in extra keys.
debaser drops keys it does not know the next time `debaser add`, `debaser remove`, or a build or rollback that records `tree` saves the list.
====
