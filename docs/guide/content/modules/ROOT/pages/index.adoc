You run a tool built from someone else's GitHub project.
You also want changes the project has not merged yet: your own branches, and open pull requests from other people.
Every time the project moves on, you fetch it again, re-apply each change, fix the conflicts, rerun the tests, and rebuild the tool by hand.

debaser turns that chore into one command.
`debaser build` gives you a runnable build of the latest project plus your changes, applied in the order you chose.
The new build replaces the installed one only after the project's recipe steps (its test and build commands) and the acceptance checks on your patches (one optional command each) have passed.
The build before it stays available as a fallback, and `debaser rollback` returns to it.

== What the parts are

debaser::
A command-line tool that keeps a patched build of someone else's GitHub project.
It rebuilds the project from its latest upstream version (the original repository) plus your patch list.
The patch list is an ordered list of changes: upstream pull requests, branches from other forks, and your own branches.
When a run stops, it says where and why.
debaser ships as one self-contained executable.

Git::
debaser does every fetch, merge, and checkout of the project through Git.
It refuses a Git older than {debaser-git-min}.

GitHub CLI (`gh`)::
debaser runs `gh pr view` to ask GitHub for a pull request's title, state, and head branch.
Without `gh`, pull requests still build, with less information about them.

Bun::
The toolchain that compiles debaser's TypeScript source into its single executable (`bun build --compile`).
You need Bun only to build debaser from source.

Coding agents::
Command-line programs that change code from a written task: Claude Code, Codex, pi, OpenCode, or any command you name.
debaser can hand a merge conflict, a failing recipe step, or a failing acceptance check to an agent, and then checks the agent's result itself.
They are optional.

== How the parts fit

You keep an ordinary clone of the project with two remotes: `upstream` for the original and `origin` for your fork.
debaser stores the patch list inside the clone's Git directory and builds in a second working directory next to the clone, the build directory.
The clone you work in stays as it was.

Each run fetches upstream and every patch, then rebases your own branches onto upstream in throwaway working directories.
In the build directory, it resets the integration branch (the branch debaser builds) to the new upstream tip and merges the patches onto it in order.
Then it runs the recipe steps and the patches' acceptance checks, and installs the result.
A recipe tells debaser how to check and build a project: named steps run in order, the build output, and where to install it.
An acceptance check is an optional command attached to one patch.
The check passes when the command exits with the expected code.
If the check also sets a pattern, the command's output must contain a match.

When a merge conflicts, a recipe step fails, or an acceptance check fails, debaser hands the problem to a coding agent through the harness, the agent integration you configure.
debaser accepts the agent's change only after it has checked the result itself.
It commits each accepted fix separately and records an accepted conflict resolution in the patch's merge commit.
Without a harness, or when the agent cannot fix the problem, the run stops with a reason, a log, and a ready-to-run prompt.

The diagram follows one `debaser build` from lock and preflight to report.
With no harness configured, the exit code names the kind of stop: 2 for a merge conflict, 3 when a patch breaks a recipe step, 4 when the step already fails on upstream, and 6 for a failing acceptance check.
When an agent tried and gave up, the run stops with exit 5 instead.

== Compared with one long-lived branch

The obvious alternative is one long-lived branch on your fork that you merge or rebase by hand.
debaser instead rebuilds the integration branch from upstream on every run.
Each patch stays separate, and you can retire one without touching the others.

Rebuilding every run does not mean resolving the same conflicts again: Git records how you resolved a conflict, and debaser replays that resolution on the next run.
A rebuild also tells you whether upstream or your patches broke a failing step: when a recipe step fails twice, debaser runs it on plain upstream, the fetched upstream commit without any patches merged, in a throwaway directory.
If the step fails there too, upstream itself is broken (exit 4); if it passes, one of your patches breaks the step (exit 3).

== Ways to run it

On a color terminal, `debaser build` shows a live view of the run, a progress card that it redraws in place.
When its output is piped, it prints plain progress lines instead.
xref:user/first-build.adoc[Your first build] walks through a run on a terminal.

With `--json`, the run prints its result as JSON on standard output: the outcome, the exit code, each patch's result, and the report's path.
xref:user/headless.adoc[Run debaser headless] covers that mode.

== Status and limits

debaser is at version {debaser-version}.
The debaser source this guide was checked against has no release workflow, so this guide installs debaser by building it from source with Bun.
Pull request sources work with GitHub only.
Only one debaser command that changes things runs at a time per xref:overview/concepts.adoc[data directory], which by default means per clone.
