A debaser command line has the form `debaser [--dir <path>] <command> [options]`.
`debaser --help` prints the usage text.
debaser accepts a few options that the usage text leaves out.
The <<global-options,global options table>> says which forms `--help` lists, and the <<options,options table>> marks the others "(not in `--help`)".

[#global-options]
== Global options

[cols="2,5,1",options="header"]
|===
|Option |Effect |In `--help`

|`--dir <path>`, `--dir=<path>`
|Sets the xref:overview/concepts.adoc#data-directory[data directory].
debaser finds the option anywhere on the command line, before or after the command.
Without `--dir`, debaser uses the `DEBASER_DIR` environment variable when it is set, else `<git-common-dir>/debaser`.
A relative path in `--dir` or `DEBASER_DIR` counts from the current directory.
|yes

|`--version`, `-V`
|Prints `debaser {debaser-version}` and exits 0.
|`--version` only

|`--help`, `-h`, `help`
|Prints the usage text on standard output and exits 0.
|`--help` only
|===

== How debaser reads a command line

[cols="1,4",options="header"]
|===
|Rule |Effect

|Options with a value
|`--name value` or `--name=value`.
A missing value is a usage error: `--<name> needs a value`.

|Flags
|Only the exact form `--name`.
`--name=<value>` is not a flag and counts as a leftover word.

|Position
|Options and flags can stand before, between, or after the positionals.

|Positionals
|Taken in order from the words that do not start with `--`, up to the number the command accepts.

|Leftover words
|An unknown option, an option of another command, or an extra positional is a usage error: `unexpected <words>`.

|Short forms
|Only `-V` and `-h`, in place of the command.
Command options have no short forms.
|===

For example, `debaser --dir /tmp/db build --rebase=conflicting --push` and `debaser build --push --dir /tmp/db --rebase conflicting` mean the same.

`--version`, `--help`, and their short forms work only in place of the command.
After a command, `--version` and `--help` are leftover words, so `debaser build --help` is a usage error.
`add` and `remove` take `-V` and `-h` as positionals, for example as `<source>`.

A usage error prints `debaser: <message>` and the usage text on standard error, and exits 1.
Running `debaser` without a command also prints the usage text on standard error and exits 1.
An unknown command is a usage error with the message `unknown command <name>`.

== Refusals at the start of a command

Each refusal exits 1.
Without color (see <<terminal-behavior>>), the message goes to standard error as a plain line.
With color, it appears in the xref:overview/concepts.adoc[live view] (`build`, `rebase`, `continue`) or in the step checklist that `rollback` draws, and otherwise as an error card on standard error.
The refusal `not inside a git repository` always goes to standard error as a plain line.

[cols="2,2,4",options="header"]
|===
|Requirement |Applies to |Refusal

|A Git repository
|every command
|`not inside a git repository`

|A patch list
|every command except `add`
|`+there is no patch list yet; add a patch first with `debaser add <source>`+`

|Git {debaser-git-min} or newer
|commands that take the lock
|`git {debaser-git-min} or newer is required (found <version>)`

|A free run lock
|commands that take the lock
|`another debaser command is running in this checkout: <command> (pid <pid>, since <time>)`, or `another debaser command is starting in this checkout (<path>)` while another command is still taking the lock
|===

debaser releases the lock when the command ends, also after Ctrl-C, a hangup, or a kill.
xref:user/headless.adoc[Running headless] covers the lock for scheduled runs, and xref:reference/files-and-codes.adoc[Files, exit codes, and environment] gives its file and every exit code.

== Commands

The last column lists what a command can ask when standard input is a terminal, followed by notes on the command.
When standard input is not a terminal, debaser asks nothing; xref:user/headless.adoc[Running headless] gives the fallback for each question.

[cols="3,4,2,6",options="header"]
|===
|Command |Options and flags |Lock, JSON (`--json`) |Terminal questions and notes

|`add <source> [description]`
|`--pin <sha>` +
`--upstream <owner>/<repo>` +
`--description <text>`
|Lock: yes +
JSON: no
|Terminal questions: none.
The first `add` creates the patch list.
See xref:user/patch-list.adoc#add-a-patch[Add a patch].

|`remove <source>`
|`--reason <text>`
|Lock: yes +
JSON: no
|Asks for the reason when `--reason` is missing; without a terminal, the command refuses.
Moves the patch to the retired patches with the date and the reason.
See xref:user/patch-list.adoc#retire[Retire a patch].

|`list`
|`--verbose` +
`--retired` +
`--json`
|Lock: no +
JSON: yes
|Terminal questions: none.
Only reads.
See xref:user/patch-list.adoc[Managing the patch list].

|`build`
|`--push` +
`--rebase <mode>` +
`--in-worktree` +
`--trust-recipe` +
`--verbose` +
`--json`
|Lock: yes +
JSON: yes
|Asks to trust a new or changed xref:recipe-author/recipes.adoc#trust[project recipe], which `--trust-recipe` answers.
Asks to force-push your rebased xref:overview/concepts.adoc#own-patch[own branches], which `--push` answers.
Works in the build directory.
See xref:user/first-build.adoc[Your first build] and xref:user/build-directory.adoc[The build directory].

|`rebase`
|`--push` +
`--rebase <mode>` +
`--in-worktree` +
`--trust-recipe` +
`--verbose` +
`--json` +
`--skip-branch`
|Lock: yes +
JSON: yes
|Asks the same questions as `build`, answered by the same options.
Only rebases your own branches onto upstream.
`rebase --skip-branch` is another spelling of `continue --skip-branch`.
See xref:user/own-branches.adoc[Rebasing your own branches].

|`continue`
|`--skip-branch` +
`--verbose` +
`--trust-recipe`
|Lock: yes +
JSON: no
|Asks the same questions as `build`, and `--trust-recipe` answers the trust question.
If the stopped run was started with `--push`, `continue` pushes without asking.
Resumes a stopped run.
A stopped build goes on in the build directory.
See xref:user/stops.adoc#continue[Continue a stopped run].

|`rollback`
|`--verbose`
|Lock: yes +
JSON: no
|Asks to trust a new or changed project recipe; no option answers it.
Undoes a stopped run, or restores the previous build.
A build is undone or restored in the build directory.
See xref:user/stops.adoc#rollback[Roll back].

|`status`
|`--fetch` +
`--json`
|Lock: no +
JSON: yes
|Terminal questions: none.
Only reads; fetches only with `--fetch`.
See xref:user/status.adoc[Reading status].

|`recipe`
|`--json` +
`--trust-recipe`
|Lock: no +
JSON: yes
|Terminal questions: none.
Only reads.
The effective recipe it prints leaves out an untrusted project recipe, and the command does not ask to trust it.
xref:recipe-author/recipes.adoc#see-the-effective-recipe[See the effective recipe] describes its output.

|`trust`
|none
|Lock: yes +
JSON: no
|Asks to confirm the trust when the project recipe is new or changed; without a terminal, the command then refuses.
Fetches the upstream branch, shows the commands of the project recipe, and records the trust after a yes.
See xref:recipe-author/recipes.adoc#trust[Trust the project's recipe].
|===

[#options]
== Options

Each row is one option for the commands it names.
An option with a different effect per command, such as `--verbose`, has one row for each effect.

[cols="2,2,5,2",options="header"]
|===
|Option |Commands |Effect |Default

|`--pin <sha>`
|`add`
|Pins the patch at a commit, given as any revision Git resolves in your clone or as a full 40-character SHA.
See xref:user/patch-list.adoc#pin[Pin a patch].
|not pinned

|`--upstream <owner>/<repo>`
|`add`
|Names the upstream repository when this `add` creates the patch list.
Any form other than `owner/repo` is a usage error.
Once the patch list exists, `add` ignores the option.
|the repository of the `upstream` remote

|`--description <text>`
|`add` (not in `--help`)
|Sets the description of the patch.
It wins over the second positional.
|the second positional, else the pull request title or the branch name

|`--reason <text>`
|`remove`
|Sets the reason stored with the retired patch.
|asked on a terminal

|`--verbose`
|`list`
|Lists the retired patches below the live ones.
|retired patches only counted

|`--retired`
|`list` (not in `--help`)
|Shows only the retired patches.
|off

|`--verbose`
|`build`, `rebase`, `continue`
|In the live view on a terminal with at least 20 rows, shows the full log with the view pinned above it.
|off

|`--verbose`
|`rollback`
|On a color terminal, shows the output of the recipe's install step in place of the checklist.
|off

|`--json`
|`list`, `build`, `rebase`, `status`, `recipe`
|Prints JSON on standard output (see <<json>>).
|off

|`--push`
|`build`, `rebase`
|Force-pushes the rebased own branches to `origin` without asking.
With `build`, it also force-pushes the integration branch to `origin` at the end of a successful build.
See xref:user/own-branches.adoc#push[Push rebased branches].
|asked on a terminal, else not pushed

|`--rebase <mode>`
|`build`, `rebase`
|Chooses which own branches the run rebases: `all`, `conflicting`, or (for `build` only) `off`.
Another value, or `off` with `rebase`, is a usage error.
See xref:user/own-branches.adoc#modes[Rebase modes].
|the patch list's `rebase` key, else `all`

|`--in-worktree`
|`build`, `rebase`
|Rebases a branch that is checked out in a worktree, such as your clone, inside that worktree instead of leaving it alone.
See xref:user/own-branches.adoc#in-worktree[Rebase a branch in its own worktree].
|off

|`--trust-recipe`
|`build`, `rebase` (not in `--help`), `continue` (not in `--help`)
|Trusts a new or changed project recipe without asking, and records the trust.
See xref:recipe-author/recipes.adoc#trust[Trust the project's recipe].
|asked on a terminal, else refused

|`--trust-recipe`
|`recipe` (not in `--help`)
|Accepted and ignored.
|none

|`--skip-branch`
|`continue`, `rebase`
|Gives up the own branch where a stopped `debaser rebase` run halted.
With any other stopped run, including a stopped `build`, debaser refuses the option.
See xref:user/own-branches.adoc#conflicts[Conflicts inside a build and in a rebase run].
|off

|`--fetch`
|`status`
|Fetches the upstream branch first; a failed fetch prints a warning and the command goes on.
See xref:user/status.adoc#fetch[Check against the latest upstream].
|no fetch
|===

== Terminal behavior

The table says when debaser asks questions, when it uses color, and which display it draws.

[cols="2,5",options="header"]
|===
|Behavior |When

|Questions
|Only when standard input is a terminal.

|Color
|Standard output is a terminal, `NO_COLOR` is unset or empty, and `TERM` is not `dumb`.

|Live view
|`build`, `rebase`, and `continue` with color and without `--json`.

|Checklist
|`rollback` with color and without `--verbose`.

|Progress lines on standard error, the summary on standard output
|Neither the live view nor the checklist is shown, and `--json` is not given (see <<json>>).
|===

[#json]
== JSON output

With `--json`, standard output holds only the JSON, and the summary lines go to standard error.
A command that ends in an error before it has a result, such as a refusal, prints no JSON; the message goes to standard error.

[cols="2,5",options="header"]
|===
|Command |Content and where it is described

|`list --json`
|An object with `config`, `upstream`, `branch`, `patches`, and `retired`; xref:user/patch-list.adoc[Managing the patch list].

|`status --json`
|The state of every patch and of upstream; xref:user/status.adoc#json[Reading status].

|`recipe --json`
|The effective recipe with the layer of each value; xref:recipe-author/recipes.adoc#see-the-effective-recipe[See the effective recipe].

|`build --json`, `rebase --json`
|The run's `result.json`; xref:user/headless.adoc#json[Running headless] and xref:reference/files-and-codes.adoc[Files, exit codes, and environment].
|===
